# Store spike — LMDB vs fsync (2026-11-24)

**Цель:** проверить, годится ли LMDB как движок control plane и какова реальная цена durability на этом хосте.
**Стенд:** a-ocode (a-ocode container, ext4 на LVM, /tmp — tmpfs). Python 3.14, `lmdb` (pip). Стенд-скрипты: `/tmp/lmdb_spike/{spike.py,bench.py,bench2.py}`.

## Метод

- 5 000 записей, объект + `changes` + `meta(rev,last_hash)` в одной транзакции, глобальный hash-chain.
- Режимы: `sync=True` (fsync на коммит), `sync=False`, батчи по 100.
- Crash-тест: 200 записей, затем `os._exit(0)` без закрытия env; повторное открытие и сверка `rev`/`changes`.
- Отдельно — стоимость `os.fsync` на 4 КБ.

## Результаты

| Режим | ops/s | Комментарий |
|---|---:|---|
| LMDB `sync=True`, 1 txn/запись | **18** | ~55 мс на коммит |
| LMDB `sync=True`, batch=100 | **1 409** | 14 commit/s, ~70 мс/коммит |
| LMDB `sync=False` | 109 710 | небезопасно для мутаций |
| raw `os.fsync` (4 КБ) | — | **47,5 мс** среднее |
| crash после 200 (batch=100, sync) | — | `rev=200`, `changes=200`, целостность ok |

## Выводы

1. **Диск — доминанта.** 47,5 мс на fsync: любой store с fsync-на-запись (SQLite, Postgres, etcd, свой журнал) упрётся в те же ~18–20 коммитов/с.
2. **Group commit обязателен.** Батч 100 даёт 1 409 записей/с; окно 2–10 мс даст десятки коммитов/с при p99 ~50–60 мс — для control plane приемлемо.
3. **LMDB переживает аварийное завершение** в пределах закоммиченных батчей; hash-chain сходится (0 разрывов на 10 000 записей).
4. **Свой файловый журнал не даёт выигрыша:** та же физика fsync + ~700 строк на сегменты/частичные записи/компакцию. LMDB — ~200 строк обёртки.
5. **`sync=False` запрещён** для мутаций: потеря последних записей при сбое.

## Ограничения замера

- Один хост, ext4/LVM, без NVMe-кэша; на другом железе числа изменятся.
- Нет конкурентной нагрузки и watch-подписчиков; только write-path.
- Crash-тест имитирует abrupt exit, не потерю питания.
