# NEMEQ_HOME_LAYOUT v0.3 — пути внутри домашнего каталога и самодостаточная поставка

**Дата:** 2026-11-26 · **Статус:** черновик к ревью · **Автор:** Верста
**Заменяет:** v0.2 (ревью Гермеса в `docs/architecture/reviews/`)
**Затрагивает:** SDD v0.5 §4, TEXTSTORE v0.3.x, ARCH_SERVICES v0.1, `massaru/layout.py`, `nqctl`, `apiserver`, `massaru/cli.py`

## 0. Нормативное правило для всех критериев этой спецификации

**Каждый критерий приёмки обязан иметь мутационную проверку**: тест, который доказывает, что критерий способен провалиться.

Формат: у критерия указано «мутант: <что сломать> → тест падает». Критерий без мутанта считается недействительным и не принимается.

Причина правила — две ошибки подряд:
- v0.1 §8.1: `grep` с `|` без `-E` искал литерал, критерий проходил вакуумно;
- v0.2 §6.3: `store_digest` не хешировал содержимое файлов, поэтому заявленный критерий «подмена байта → digest расходится» из формулы не следовал.

Обе ошибки одного класса: критерий описывал намерение, а не проверку.

## 2. Принципы

### 2.1 Два разных утверждения о зависимостях

**(а) Нет сетевых и пакетных зависимостей.** Обязательно и проверяемо: нет `pip install` из сети, нет `ensurepip`, нет `virtualenv`, нет обращений к pypi/зеркалам/реестрам во время install и запуска. Отсутствие `pip`/`ensurepip` в `PATH` — норма, а не повод падать.

**(б) Хостовые предпосылки объявлены и проверяются.** Ложь «зависимостей нет» выключает проверку, поэтому предпосылки названы и валидируются preflight.

**Матрица поддерживаемых ABI** (проверяется до создания каталогов):

| Предпосылка | Требование | Проверка | Код отказа |
|---|---|---|---|
| CPython | `>=3.12,<3.13` | `sys.version_info` | 2 |
| архитектура | `x86_64` | `platform.machine()` | 2 |
| glibc | ≥ версии в `deps.lock` (поле `min_glibc`), не «под которую собраны» | `platform.libc_ver()` → сравнение с `min_glibc` | 2 |
| системные библиотеки | список из `deps.lock` (`libssl`, `libffi`, `libz` при нативных колёсах) | `ctypes.util.find_library` по каждому | 2 |
| ФС стора | локальная, POSIX `flock`, атомарный `rename`, `fsync` | `stat -f`; NFS/overlay/CIFS → отказ | 8 |
| внешние утилиты | allow-list §2.3 | `doctor` | 2 |

Проверка glibc по `min_glibc` из манифеста, а не «по факту сборки», устраняет расплывчатость: значение фиксируется при сборке дистрибутива и попадает в `deps.lock`.

**Rust-этап.** Target `x86_64-unknown-linux-musl` сам по себе не гарантирует статическую сборку. Требование формулируется проверяемо:

- `readelf -d` на собранном артефакте не содержит `NEEDED` (кроме допустимого пустого списка);
- бинарь запускается на минимальной целевой системе без установленных библиотек;
- проверка входит в CI сборки, а не в приёмочный тест спецификации.

**Мутант:** добавить в `deps.lock` `min_glibc` выше текущей → `install` отказывает с кодом 2 до создания каталогов.

### 2.2 Целевая платформа — Rust

Переходное правило: Python-поставка обязана вести себя так, будто Rust-бинарь уже есть. Всё, что нарушает, — техдолг D1–D7 (§10) с датами.

### 2.3 Allow-list внешних утилит

Разрешено: `systemctl`, `systemctl --user`. Запрещено: `cp`, `rsync`, `sha256sum`, `unzip`, `tar`. Всё внутрипроцессно (`shutil.copy2` + явные режимы + `os.fsync`, `hashlib`, `zipfile`).

**Мутант:** заменить `shutil.copy2` на вызов `cp` → тест `strace -f -e trace=execve` падает.

### 2.4 Барьер `sys.path`

При старте `sys.path` очищается до `$NEMEQ_HOME/lib/nemeq-core` и `$NEMEQ_HOME/lib/pydeps` (через `site.addsitedir`). Остальное удаляется; импорт не из `lib/` — падение с явной ошибкой.

**Мутант:** вернуть `site-packages` в `sys.path` → тест «враждебный PYTHONPATH» падает.

### 2.5 Поставка зависимостей

Источник истины — `wheelhouse/` + `manifest.sha256`. Распаковка при install.

**Ограничение формата (закрывает S2).** Поддерживаются только чистые колёса: `*.whl` без `*.data/` и без `.pth`-файлов внутри. Наличие неподдерживаемого элемента — **отказ до записи в `lib/pydeps`** с перечислением файлов.

Если формат нужен шире — включается offline-installer (не `pip`, а собственный разворачиватель, понимающий `data`/`.pth`), и это отдельное решение, а не подразумеваемое.

Порядок:
1. сверка sha256 каждого колеса с манифестом;
2. проверка допустимости формата (шаг выше);
3. распаковка с сохранением `.dist-info`;
4. сверка `RECORD` пофайлово уже **после** распаковки, по итоговой раскладке;
5. предкомпиляция `.pyc` в `__pycache__` рядом с модулями (§4.3).

**Мутант:** подменить один байт в колесе → `deps install` отказывает с кодом 9. Добавить в колесо `.pth` → отказ с перечислением до записи.

## 4. Раскладка

```
$NEMEQ_HOME/                          # префикс (по умолчанию ~/.nemeq)
├── config/home.toml                  # home_id, layout_version  ← уровень ПРЕФИКСА
├── bin/                              # шимы
├── lib/                              # immutable: nemeq-core/, pydeps/, INSTALL.json
└── instances/<name>/
    ├── config/instance.toml          # instance_id, schema_version, port, store_path  ← уровень ИНСТАНСА
    ├── var/                          # mutable-корень
    │   ├── store/                    # здесь же lock (§6.4)
    │   ├── epishu/<id>/
    │   ├── state/
    │   ├── data/
    │   ├── tmp/
    │   └── pycache/                  # не используется при контракте §4.3, оставлен пустым
    ├── logs/
    └── run/                          # pid, instance.json, migration.json
```

### 4.1 Полная таблица преобразования (закрывает S3)

Правило «строго 1:1» верно только для элементов верхнего уровня и **не охватывает** переименование `apiserver` → `store`. Полная таблица:

| Источник (legacy) | Цель | Тип |
|---|---|---|
| `/var/nemeq/apiserver/` | `<inst>/var/store/` | каталог, **переименование** |
| `/var/nemeq/epishu/` | `<inst>/var/epishu/` | каталог, 1:1 |
| `/var/nemeq/state/` | `<inst>/var/state/` | каталог, 1:1 |
| `/var/nemeq/data/` | `<inst>/var/data/` | каталог, 1:1 |
| `/var/nemeq/` (прочее) | — | **нет правила → отказ, код 7** |
| `/opt/nemeq/` | `$NEMEQ_HOME/lib/` | каталог (immutable) |
| `/run/nemeq/` | `<inst>/run/` | не переносится (runtime), пересоздаётся |

**Уровень вложенности.** Все элементы внутри `epishu/<id>/` (`wal/`, `atoms/`, `traces/`, `state/`, `view/`, `paqidutu/`, `zikru-zi/`, `zikru-su/`, `raw/`, `archive/`, `observability_log/`) остаются **внутри каждого** `epishu/<id>/` без изменения уровня. Они не поднимаются в `var/`.

**Мутант:** добавить в источник файл вне таблицы → `migrate` отказывает с кодом 7 и именем файла.

### 4.2 Контракт `epishu/<id>/` не меняется

Три вещи, которые его ломают, и их запрет:

1. **Абсолютные пути внутри данных** — в атомах, трейсах, `observability_log` только пути относительно `<store_root>`. `fsck` находит любую строку, начинающуюся с `/`, в метаданных.
2. **ФС стора** — NFS/overlay/CIFS не дают гарантий `flock`/`rename`. Отказ с кодом 8.
3. **Глубина вложенности** — код не вычисляет пути от числа уровней, только через резолверы.

**Мутант:** вписать `/var/nemeq/...` в метаданные атома → `fsck` падает.

### 4.3 Контракт байткода и иммутабельность `lib/` (закрывает B9)

Три механизма в v0.2 противоречили друг другу: `PYTHONPYCACHEPREFIX` перенаправляет кэш, `PYTHONDONTWRITEBYTECODE=1` запрещает запись, а поставленные `.pyc` могут оказаться не там, откуда их ищет запуск с отключённой записью. Контракт v0.3 — один:

| Момент | Что делается |
|---|---|
| install | `compileall` пишет `.pyc` в `lib/nemeq-core/__pycache__/` и `lib/pydeps/**/__pycache__/` — то есть **туда, где Python их ищет** |
| runtime | `PYTHONDONTWRITEBYTECODE=1` во всех шимах и дочерних процессах; `sys.pycache_prefix` **не задаётся** |
| `var/pycache` | не используется; каталог оставлен для будущих нужд, но контрактом не задействован |

**Threat model, названный явно:**
- `lib/` защищён от **случайной** записи: права `0555` + отсутствие записи байткода + тест.
- `lib/` **не** защищён от процесса того же UID: владелец всегда может снять права. Реальный барьер — только системный (`ReadOnlyPaths`/`ProtectSystem`), и он в user-unit доступен не везде.
- Обещать защиту от своего UID без реального барьера — запрещено этой спецификацией.

**Мутант:** запустить сервис с `PYTHONDONTWRITEBYTECODE` не выставленным → тест «lib не изменился» падает (появляется `__pycache__`).

### 4.4 `var/tmp/` обязателен

`rename` атомарен только в пределах одной ФС. Staging в `/tmp` (tmpfs) даст `EXDEV`. `var/tmp/` (0700) — все атомарные записи; `doctor` сверяет `st_dev(var/tmp) == st_dev(var/epishu)`.

**Мутант:** смонтировать `var/tmp` на отдельную ФС → `doctor` падает.

### 4.5 Манифест установки

`lib/INSTALL.json`: `layout_version`, `nemeq_version`, `schema_version`, `platform_tag`, `deps_lock_sha256`, `min_glibc`, `build_id`, `installed_at`.

Код отказывается открывать стор со схемой новее своей.

**Мутант:** увеличить `schema_version` в `instance.toml` на 1 → сервис не стартует, сообщение «store schema N > supported M».

### 4.6 Сокеты и длина пути

`sun_path` — 108 байт. Валидация в `install`/`doctor`, порог 100; для длинных HOME — `var/run-short` (0700) или abstract sockets.

**Мутант:** `HOME` длиной 120 → `doctor` падает до старта.

### 4.7 Квоты и права

`0700` на `var/`, `0600` на файлы и `instance.toml` (там могут быть токены), umask `077`. `max_state_bytes` + soft-лимит 80 % в лог. `doctor` проверяет права, место и UID всех файлов.

**Мутант:** `install` при umask 000 → `stat -c %a var` = 700 (иначе падение). Один файл сменить на другой UID → `doctor` падает.

### 4.8 `run/` без overlay

Overlay — это `mount()`, то есть root. `run/` — только pid, lock-ссылка, сокеты, `instance.json`, `migration.json`. Overlay либо `var/overlay/`, либо уровень (в) вне этого документа.

**Мутант:** добавить overlay в `run/` → архитектурный тест падает.

## 5. Резолвинг

```
home:     --home       > NEMEQ_HOME     > $HOME/.nemeq
instance: --instance   > NEMEQ_INSTANCE > "default"
var:      --state-root > NEMEQ_VAR_ROOT > <home>/instances/<instance>/var
store:    --store      > NEMEQ_STORE    > <var>/store
```

**Правила:**

1. Все переопределения абсолютны. Относительный путь — код 2, не «приведём от CWD».
2. `--state-root`/`--store` вне `<home>` — только с `--allow-outside-home`.
3. При env-переопределении — `source=env(NEMEQ_VAR_ROOT)` в `nqctl status`.
4. `$HOME` пуст/отсутствует и нет `--home`/`NEMEQ_HOME` → код 2. Никогда не фоллбэчить на CWD или `/`.
5. Каталоги создаёт только `install`/`migrate`. `apiserver` без `init` → `NemeqNotInitialized`.
6. **Имя инстанса** валидируется как один безопасный компонент: `^[a-z0-9][a-z0-9_-]{0,31}$`. `..`, `/`, `\`, NUL — отказ до файловых операций.
7. **Каноникализация:** все пути приводятся `os.path.realpath` до сравнения; сравнение store идёт по realpath, не по строке.

**Мутанты:** относительный `NEMEQ_HOME=./x` → код 2. `--instance ../x` → код 2. `env -u HOME` → код 2.

## 6. Инстансы

### 6.1 Идентичность: два разных UUID

| Уровень | Файл | Поле | Что идентифицирует |
|---|---|---|---|
| префикс | `$NEMEQ_HOME/config/home.toml` | `home_id` | установку (одна на `$NEMEQ_HOME`) |
| инстанс | `<inst>/config/instance.toml` | `instance_id` | **стор** конкретного инстанса |

`instance_id` дублируется в метаданных стора. При старте сверяются оба: `home_id` конфига против `home.toml`, `instance_id` конфига против метаданных стора. Расхождение → код 5.

**Мутант:** подменить `instance_id` в `instance.toml` → сервис не стартует с кодом 5. Подменить в одном инстансе → второй работает (проверка независимости).

### 6.2 Порты

Дефолт — **фиксированный `8448`**. При занятом порте — отказ с кодом 3 и именем владельца (поиск по `instances/*/run/instance.json`), **без автоинкремента**. Эфемерный `0` — явная опция для сценариев, где клиент читает адрес из `run/instance.json`.

`run/instance.json`: `{name, home_id, instance_id, pid, port, started_at, store_realpath}`.

**Мутант:** два инстанса с портом 8448 → второй падает с кодом 3, сообщение называет виновника, в стор не пишет.

### 6.3 Жизненный цикл

`nqctl instance create|list|status|destroy`. `create` — `0700`/`0600`; `destroy` требует остановленного сервиса, берёт лок, удаляет `var/ config/ logs/ run/`, `lib/` не трогает.

**Мутант:** `destroy` при живом сервисе → код 4. После destroy `lib/` на месте.

### 6.4 Лок живёт в сторе, не в инстансе (закрывает B5)

В v0.2 lock лежал в `instances/<name>/run/`, поэтому два инстанса с разными именами, но одним `--store`, получали **разные** локи и писали одновременно.

Лок теперь привязан к самому стору:

```
<store>/lock
open(O_RDWR|O_CREAT|O_NOFOLLOW, 0600)
flock(LOCK_EX|LOCK_NB)
```

Это совпадает с текущей реализацией `massaru.store` (сообщение `StoreBusy: another writer holds <store>/lock`), то есть спецификация не вводит новое поведение, а фиксирует существующее.

Занят → код 4 и `store busy: pid N`. Абсолютный запрет: любые фиксированные пути вне стора.

**Мутанты:** два инстанса с разным именем и одним `--store` → второй падает с кодом 4. Два разных стора → оба живы. `strace` показывает ровно один `openat` lock-файла внутри стора.

### 6.5 systemd

Дефолт — user-unit `~/.config/systemd/user/nemeq-<instance>.service`. Системные unit — только уровень (в). Абсолютный путь прописывает `nqctl install-unit`; `%h` **запрещён** (в системном юните даёт HOME менеджера, а не `User=`).

**Writable paths сужены** (закрывает часть B9):

```
Environment=NEMEQ_HOME=<abs>
Environment=NEMEQ_INSTANCE=<name>
ExecStart=<abs>/bin/nqctl serve
Restart=on-failure
KillMode=mixed
TimeoutStopSec=20
NoNewPrivileges=yes
PrivateTmp=yes
ProtectSystem=strict
ReadWritePaths=<abs>/instances/<name>/var
ReadWritePaths=<abs>/instances/<name>/logs
ReadWritePaths=<abs>/instances/<name>/run
ReadOnlyPaths=<abs>/lib
```

**Lingering.** Явно: по умолчанию сервис живёт, пока активна пользовательская сессия. Работа после logout и на загрузке требует `loginctl enable-linger <user>` и это описано как отдельное действие с привилегией (выполняется один раз, обычно администратором). Обещать работу «после reboot» без lingering запрещено.

**Мутант:** `grep -c '%h' unit` = 0. Попытка записи в `lib/` из-под unit → отказ. Тест lingering: без `enable-linger` сервис не поднимается после logout, с ним — поднимается.

## 7. Миграция

### 7.1 Предусловия

- сервис **остановлен**; при живом — код 2 и текст «stop nemeq-<i> first»;
- `--force` не существует;
- target непуст → код 2, если не `--merge`;
- locks источника и target удерживаются **всё** время миграции (§7.2).

### 7.2 Crash-safe состояние (закрывает B8)

Файл `run/migration.json` + `fsync` файла и каталога `run/` на каждом переходе.

| Состояние | Что уже сделано | Что делает повторный запуск |
|---|---|---|
| `prepared` | маркер записан и `fsync`, staging создан | удаляет staging, начинает заново (или `--continue` продолжает) |
| `copying` | идёт копирование | `--continue` дописывает по манифесту; без флага — перезапуск |
| `verifying` | копия готова, идёт fsck+digest | повторяет проверку |
| `published` | `rename` выполнен | дописывает отчёт из манифеста staging-метаданных |
| `reported` | отчёт записан | ничего, успех |
| `failed:<reason>` | ошибка | печатает причину, требует явного `--restart` |

**Порядок (нормативный):**

1. взять лок источника (exclusive) и лок target;
2. проверить `st_dev(staging_parent) == st_dev(target_var)` — staging **на ФС target**;
3. записать `prepared` + `fsync` файла + `fsync` каталога `run/`;
4. создать `var.migrating-<ts>/` и записать в него манифест копирования;
5. копировать пофайлово; после завершения — один проход `fsync` по всем файлам и каталогам staging;
6. `verifying`: `fsck` strict + сравнение `store_digest` источник↔staging;
7. `chown` по режиму §7.4; повторный `fsync`;
8. `rename(staging → var)`; `fsync` родительского каталога;
9. `published`; записать отчёт `run/migration-report.json` + `fsync`;
10. `reported`; отпустить локи.

**Восстановление:** `kill -9` на любом шаге оставляет состояние, из которого повторный запуск либо завершает, либо откатывает — но **никогда** не публикует частичный `var/`.

**Мутанты** (fault injection на каждом переходе, включая после rename и до записи отчёта): целевой `var/` либо отсутствует полностью, либо опубликован полностью; источник не изменён (mtime/размер до и после).

### 7.3 `store_digest` — по содержимому, а не по счётчикам (закрывает B1)

В v0.2 формула включала `atom_count`, но не хеши содержимого, поэтому подмена байта в `atoms` digest не меняла.

Каноническое кодирование (устраняет неоднозначную конкатенацию):

```
D = конкатенация по возрастанию relpath (UTF-8, NFC):
      u64be(len(relpath)) || relpath ||
      u8(kind)                       # 0=file, 1=symlink
      file:    u64be(size) || sha256(content)
      symlink: u64be(len(target)) || target
store_digest = "sha256:" + sha256(D)
```

Обходятся **все** файлы под `<store>` (`store/`, `epishu/`, `state/`, `data/`, `anchor*`, включая `wal/`, `view/`, `paqidutu/`, `zikru-*`, `observability_log/`). Каталоги не включаются отдельными записями — они покрыты путями файлов. Пустые каталоги фиксируются отдельным списком `dirs[]` в отчёте.

**Sampling запрещён.** Ускорение — только Merkle-дерево как оптимизация с сохранением полноты, и это отдельное решение.

**Мутанты:** подмена одного байта в файле **каждого** класса (`atoms`, `view`, `paqidutu`, `wal`, `anchor`, `state`, `data`) → digest меняется. Перестановка порядка обхода → digest не меняется. Добавление пустого каталога → меняется `dirs[]`.

### 7.4 Режимы миграции (закрывает B4)

В v0.2 противоречие: `chown` требует root, а §0.1 запрещает root.

Два явных режима, режим определяется по владельцу источника и **печатается в отчёте**:

| Режим | Когда | Требования | Поведение |
|---|---|---|---|
| **rootless** | источник целиком принадлежит целевому uid | запуск от целевого пользователя | `chown` не нужен; файлы чужих uid → отказ с перечнем |
| **root-assisted** | источник принадлежит root или есть чужие uid | запуск от root + явный `--root-assisted --target-uid N --target-gid N` | после копирования `chown -R`; `--target-uid 0` запрещён |

**Запуск от root без `--root-assisted` — отказ** (код 2), чтобы привилегия не применялась молча. Если в источнике есть файлы третьих uid (не root, не целевой) — отказ с перечнем в обоих режимах.

**Мутанты:** root-owned фикстура без `--root-assisted` → код 2. С флагом → успех, целевые файлы принадлежат `--target-uid`. Файл третьего uid → отказ с перечнем, источник не изменён.

### 7.5 Symlink

Копировать как ссылки, без dereference. Абсолютная ссылка, чей target вне источника — в отчёт и отказ по умолчанию (`--rewrite-links` для переписывания префикса). Симлинк наружу источника — всегда отказ.

**Мутанты:** `var/x -> /var/nemeq/var/y` → отказ, путь в отчёте. Относительная ссылка внутри стора → копируется как `lrwxrwxrwx`, `readlink` идентичен.

### 7.6 Anchor и незавершённые транзакции

Копируется явно: `store/`, `var/epishu/`, `var/state/`, `var/data/`, **`anchor*`**. `fsck` источника — strict. Непустой хвост WAL → по умолчанию код 6; `--recover` реплеит WAL в staging, после чего digest сравнивается **после** реплея на обеих сторонах.

**Мутанты:** оборванная транзакция → код 6 с перечнем. С `--recover` → digest совпадает, отчёт фиксирует число реплеенных записей, источник не изменён.

### 7.7 Источник не удаляется никогда (закрывает B2)

Флаг `--purge-source` **удалён**. Вместо него отдельная команда:

```
nqctl migrate --print-cleanup-cmd
```

Она **печатает** готовую команду удаления источника и **ничего не выполняет**. Никакой сценарий `migrate` не удаляет источник — ни при успехе, ни при ошибке.

**Мутант:** после успешной миграции источник на месте; в stdout есть команда, готовая к копированию.

### 7.8 Version skew

В отчёт пишутся `source_version`, `target_version`, `format_version`. `format_version` вне поддерживаемого диапазона → код 7. Несовпадение `schema_version` → код 5.

### 7.9 Коды возврата (закрывает B3)

| Код | Класс | Примеры |
|---|---|---|
| 0 | успех | — |
| 2 | неверный вызов или предусловие | сервис запущен, target непуст, относительный путь, root без `--root-assisted`, неверное имя инстанса |
| 3 | порт занят | `EADDRINUSE` |
| 4 | лок занят | `store busy: pid N` |
| 5 | несовпадение идентичности или схемы | `home_id`, `instance_id`, `schema_version` |
| 6 | грязный WAL | нужен `--recover` |
| 7 | нет правила преобразования / версия вне диапазона | неизвестный файл, симлинк наружу, `format_version` |
| 8 | неподдерживаемая ФС | NFS/overlay/CIFS |
| 9 | расхождение хеша **поставки** | колесо не совпало с `manifest.sha256` |
| 10 | расхождение `store_digest` **данных** | источник и staging не совпали |
| 11 | ошибка ввода-вывода | чтение/запись/`fsync`/`chown` |
| 12 | сбой health-check на target | в сценарии `--verify-target` |

**Приоритет при нескольких ошибках:** 2 (вызов) → 4 (лок) → 8 (ФС) → 7 (правило) → 6 (WAL) → 5 (схема) → 11 (I/O) → 9/10 (хеши) → 12 (health). То есть сначала проверяется, можно ли вообще начинать, потом — совместимость, потом — данные.

**Мутант:** для каждой строки — отдельный тест с точным кодом и проверкой отсутствия частичных изменений.

### 7.10 Переход уже развёрнутых alpha/beta (закрывает B7)

В v0.2 правило «разные версии — разные HOME» не говорило, что делать с двумя существующими HOME, у каждого свой `lib/` и конфиг.

Отдельный сценарий, **без автоматического слияния HOME**:

```
nqctl migrate --from-home /root/.nemeq --into-instance alpha --use-lib-from /root/.nemeq
```

Порядок:

1. прочитать `home.toml` и `instance.toml` источника: `layout_version`, `nemeq_version`, `schema_version`;
2. сравнить `schema_version` источника с поддерживаемой целевым `lib/` → выше: код 5;
3. сравнить `nemeq_version`: расхождение → предупреждение и требование `--accept-version-skew`, иначе код 6;
4. скопировать **только данные** (`var/`) в целевой инстанс; `lib/` берётся из `--use-lib-from`, а не из источника;
5. `instance_id` источника сохраняется как `instance_id` нового инстанса (это тот же стор); при коллизии — код 5;
6. каждый HOME мигрируется **отдельно**; слияние двух HOME в один инстанс запрещено (код 2);
7. после обеих миграций `nqctl instance list` показывает оба, `lib/` один.

**Мутанты:** две фикстуры с разными `schema_version` → отказ код 5, источники не изменены. С одинаковыми → оба мигрируют, `lib/` один (`find lib -maxdepth 1 | wc -l` не растёт). Попытка слить две HOME в один инстанс → код 2.

## 8. Критерии приёмки

Каждый критерий сопровождается мутантом (§0).

### 8.1 Ни одного пути ОС в исполняемых файлах и конфигурации

В v0.2 проверялись только `*.py`, что пропускало Rust, shell и unit-файлы.

```sh
git grep -nE '/(var|opt|run)/nemeq' \
  -- '*.py' '*.rs' '*.sh' '*.toml' '*.service' \
  ':!massaru/legacy.py' ':!tests/fixtures/*'
```

пусто. Архитектурный тест: строки допустимы только в `massaru/legacy.py`.

**Мутант:** добавить `/var/nemeq` в `.rs`, `.sh` и `.service` по очереди → тест падает в каждом случае. Добавить в `legacy.py` → остаётся зелёным.

### 8.2 Изоляция инстансов

Автотест: один id в двух инстансах с **разным** содержимым, оба читаются независимо; `realpath` сторов не пересекаются, inode разные; второй старт на том же сторе → код 4.

**Мутант:** подменить `NEMEQ_HOME` второго инстанса на первый → тест падает.

### 8.3 Health как контракт

`{instance, home_id, instance_id, rev, last_hash, fsck: clean}`. До и после `restart`: `rev` не убывает, `last_hash` совпадает, идентификаторы те же.

**Мутант:** остановить стор → health отдаёт non-200.

### 8.4 Целостность данных через `store_digest`

Сравнение digest по §7.3, не пара `rev`+`last_hash`.

**Мутант:** подменить байт в `atoms` → digest расходится, миграция не успешна (код 10).

### 8.5 Чистота вне HOME

Полный набор файловых syscall'ов (`openat`, `open`, `creat`, `mkdirat`, `mkdir`, `rename`, `renameat`, `linkat`, `symlinkat`, `unlinkat`), затем проверка **фактических изменений** вне HOME (снимок дерева до/после), а не только флагов открытия — в v0.2 фильтр по `O_CREAT|O_WRONLY` пропускал запись в существующий файл.

Allow-list: `/dev/null`, `/proc/self`, сокет systemd, `$XDG_RUNTIME_DIR` (осознанно).

**Мутант:** записать в существующий файл вне HOME → тест падает.

### 8.6 Установка без сети и без pip

1. `unshare -n` — install и старт проходят;
2. с сетью + `strace -e connect,sendto` — ноль попыток наружу;
3. `pip`/`ensurepip` отсутствуют в `PATH` (проверяется в тесте);
4. smoke-импорт каждого пакета из `deps.lock`.

**Мутант:** добавить `urllib.request` вызов в install → тест (2) падает.

### 8.7 Негативные сценарии миграции

Каждый — тест с кодом и состоянием target: сервис запущен (2), target непуст (2), неизвестный файл (7), грязный WAL (6), симлинк наружу (7), `kill -9` посреди копирования (staged, маркер), файл третьего uid (отказ с перечнем), расхождение digest (10), порт занят (3), лок занят (4).

### 8.8 Работа без root, идемпотентность, жизненный цикл

1. install и старт от непривилегированного пользователя, без sudo;
2. повторный `install` поверх существующего HOME сохраняет `rev`/`last_hash`, не плодит инстансы;
3. `nqctl uninstall [--purge]` не оставляет процессов, локов, unit'ов;
4. гонка старта: два одновременных запуска на одном сторе — ровно один жив, второй код 4;
5. HOME с пробелом и не-ASCII;
6. NFS → отказ при старте с кодом 8;
7. `nqctl doctor --json` как артефакт приёмки;
8. UID всех файлов в HOME равен владельцу.

### 8.9 Симлинк `var` не является авторитетным (закрывает S6)

Симлинк `$NEMEQ_HOME/var -> instances/default/var` создаётся **только** при install для совместимости. Путями он не служит: все вычисления — через резолверы. `doctor` проверяет, что симлинк указывает строго на `instances/default/var`; иначе отказ.

**Мутант:** перенаправить симлинк на `instances/alpha/var` → `doctor` падает до любой записи.

## 11. Открытые вопросы

1. **`dirs[]` в `store_digest`.** Пустые каталоги фиксируются отдельным списком. Достаточно ли списка, или включать их в основной поток через запись `kind=2`?
2. **`--accept-version-skew`.** Нужен ли он вообще, или при расхождении `nemeq_version` всегда отказ (проще и строже)?
3. **`ReadOnlyPaths` в user-unit.** Доступен ли в целевой версии systemd; если нет — достаточно ли `ProtectSystem=strict` + узких `ReadWritePaths`?
4. **Merkle для большого стора.** Нужен ли сразу, или отложить до замера полного digest на 1M rev?
5. **`--verify-target` (roundtrip).** Делать в отдельном migration-check namespace (не меняет `rev` target) или на финальном target с фиксацией ожидаемой ревизии в отчёте?
