## 1. Решение

Источник истины — **append-only журнал JSONL**; состояние — материализация; MD/CSV — представления. Ноль зависимостей, audit by construction.

Цена: ~700–900 строк + тесты (выросла после закрытия стопперов). Это осознанный обмен кода на прозрачность.

## 2. Формат

```
/var/nemeq/apiserver/
├── lock                     # flock: один писатель
├── log/000001.jsonl         # сегменты 64 МБ
├── snap/0001000.json        # снапшот состояния
├── anchor/0001000.anchor    # подписанный якорь (rev, hash)
├── state/epishu/*.json      # материализация (НЕ истина)
├── views/index.md, audit.csv
└── meta.json                # fmt, committedOffset, rev, last_hash, anchor
```

Запись:
```json
{"fmt":1,"rev":1235,"prev":"sha256:…","ts":"…","actor":"versta",
 "requestId":"…","txn":[{"op":"put","key":"epishu/octavia","value":{…}}],
 "hash":"sha256:…"}
```

- `hash = sha256(JCS({fmt,rev,prev,ts,actor,requestId,txn}))` — **все** аудит-поля, не только txn.
- JCS (RFC 8785): сортировка ключей, NFC, без NaN/Inf, без экспонент; golden-векторы в тестах.
- `prev` — hash предыдущей строки; цепочка глобальная.

### 2.1. Лимиты и кодировка (до записи)

- value ≤ **1 МиБ**, строка журнала ≤ **2 МиБ**; больше → **413**, в журнал не попадает.
- Только валидный UTF-8; иначе **400**.
- Ключ: `resource/name`, `name` — `[a-z0-9][a-z0-9.-]{0,62}`.
- Неизвестные поля в `value` — сохраняются, читаются forward-compatible; ломающие изменения — новая версия ресурса (`v1alpha2`), не переписывание журнала.

### 2.2. Почему JSONL, а не CSV/MD

| Формат | Истина | Почему |
|---|---|---|
| JSONL | **да** | вложенность, канонизация, атомарная строка, hash |
| CSV | нет | нет вложенности/транзакций; только audit-выгрузка |
| Markdown | нет | парсинг неоднозначен; манифест/просмотр |
| YAML | нет | то же; вход `nqctl apply` |

## 3. Путь записи (главное исправление v0.2)

1. **Один писатель** (`flock`); второй — `EBUSY`.
2. **Сборка батча под локом писателя**: CAS (`expected_rev`) проверяется в момент сборки, а не после записи. N параллельных update с одним `expected_rev` → ровно один 200, остальные 409.
3. **Запись батча**: запомнить `batchStartOffset` → write всех строк → `fsync`.
4. **Ошибка write/fsync/ENOSPC/EIO**:
   - `ftruncate(batchStartOffset)` → `fsync` → **store переходит в `read-only`** (fail-stop);
   - клиент получает 5xx; `rev` не двигается; ретрай идемпотентен;
   - выход из `read-only` — только `nqctl store fsck --repair` (хвост) или restore.
   - **Никогда** не оставляем частичный батч в середине.
5. **Публикация**: `meta.committedOffset` и `rev` обновляются **после** fsync; читатели и watch видят только `offset ≤ committedOffset`.
6. **Ответ 200** — только после публикации.
7. **Дедуп `requestId`**: индекс персистентен (восстанавливается из журнала), окно 24 ч; повтор в окне → та же `rev`; после окна — документированный новый эффект.

### 3.1. Замер (этот хост, ext4/LVM, 24.11)

| batch | ops/s | commits/s |
|---:|---:|---:|
| 1 | **20** | 20 |
| 10 | 191 | 19 |
| 100 | **1 922** | 19 |
| 1 000 | 12 662 | 13 |
| raw fsync 4 КБ | — | **47,5 мс** |

5 000 записей = 1,33 МБ (~266 Б/запись). **Потолок без батча ≈ 21 коммит/с.**

---

## 4. Целостность и обнаружение усечения

1. Hash покрывает **всю** запись (fmt/rev/prev/ts/actor/requestId/txn).
2. **Подписанный якорь** каждые 1 000 ревизий: `anchor/<rev>.anchor` = `{rev, hash, sig}` (HMAC ключом apiserver; публичная часть/копия — off-host). Якорь входит в `meta`.
3. **fsck**:
   - цепочка/`rev`/JCS — обязательны;
   - `committedOffset` совпадает с последней валидной строкой;
   - `rev`/`hash` не меньше последнего якоря;
   - **усечение хвоста ниже якоря → FAIL**, старт запрещён (не «torn tail»).
4. **Torn tail** (обрыв без `\n`) — единственный автоматически чинимый случай: обрезать до последней валидной строки, записать `repair`-событие в audit.
5. **Битая середина** → карантин, restore из снапшота+сегментов+архива; автопродолжение запрещено.
6. **Пересчёт цепочки** после подмены: без ключа якоря не пройдёт; с ключом — компрометация хоста, якорь off-host показывает расхождение.

---

## 5. Снапшоты, компакция, retention

- Снапшот каждые 1 000 ревизий/5 мин: `{rev, hash, state}`; temp → fsync → rename → fsync(dir); храним 2.
- `verify` сверяет снапшот с цепочкой и якорем.
- Компакция: после снапшота — ротация сегмента; старые сегменты **не удаляются** без off-host архива (аудит).
- Retention/архив — политика владельца; по умолчанию: горячие 30 дней, архив 1 год.
- **Резерв диска:** 10% под снапшот/fsck; при 80% — алерт, при 90% — read-only (507).

---

## 6. Watch (исправленная семантика)

1. **Subscribe-then-replay**: сначала регистрируем подписчика с курсором `fromRev`, затем читаем backlog с диска, затем live; дедуп по `(rev, seq)`.
2. Публикация только после fsync; событие содержит `rev`, `seq`, `type`, `key`, `resourceVersion`.
3. **Bounded buffer** на подписчика (10 000 событий); переполнение → закрыть поток **410 Gone** с `resourceVersion` для relist. Медленный читатель не роняет API.
4. Bookmark каждые 100 ревизий.
5. **Authz на каждое событие**: scope объекта мог смениться; фильтр по scope при доставке.
6. Отмена — `context cancellation`; reader не держит writer-lock.

---

## 7. API-контракт для контроллеров

- **`rev`** (глобальный, int) — для watch/bookmarks; **`resourceVersion`** (строка `"<rev>-<uid8>"`) — для CAS объекта.
- `metadata.generation` (spec) и `status.observedGeneration`; контроллер подтверждает, что увидел новую generation.
- Устаревший `resourceVersion` → **410 Expired**, клиент делает relist.
- **Lease** — объект для лидерства контроллеров (один active session на epishu).
- **Finalizers**: удаление Epishu → session stop → снятие finalizer → tombstone.
- `dryRun`, `limit/continue` (пагинация), `fieldSelector`, `labelSelector`.
- Ошибки: `409 Conflict`, `410 Expired`, `413 TooLarge`, `422 Invalid`, `507 InsufficientStorage`.

## 8. Производительность и SLO (исправлено)

При fsync 47,5 мс заявлять write p99 < 50 мс нельзя — арифметически невозможно.

| Метрика | SLO v1 | Как мерить |
|---|---|---|
| Read p99 (get/list) | ≤ 50 мс | гистограмма при 20/50/100 rps |
| Write p99 (put/delete) | ≤ 150 мс при ≤50 rps | end-to-end, включая admission+hash+fsync |
| Write p95 | ≤ 100 мс | то же |
| Replay 1 млн rev | ≤ 60 с (снапшот + хвост) | замер до P0 |
| fsck 1 млн rev | ≤ 120 с | замер до P0 |

Group commit: окно 2–10 мс; батч не больше 1 000 записей; backpressure — 429 при переполнении очереди.

---

## 9. Безопасность (v1)

- Каталог 0700, файлы 0600, владелец `nemeq`; открытие с `O_NOFOLLOW`, проверка inode/устройства каталога при старте.
- Секреты — только `secretRef`; redaction в ошибках/логах; тест «0 секретов в журнале».
- Watch/list — authz по scope на каждое событие, не только на подписку.
- **Audit отклонённых admission-запросов** — отдельные `AUDIT_DENY`-записи (txn пустой), иначе атаки невидимы.
- Якоря подписаны и копируются off-host; без этого hash-chain не защищает от «усечь хвост + переписать meta».
- `chattr +a` на сегменты — опционально (ротация создаёт новый файл).

---

## 10. Тесты (обязательные до P0)

1. Property-based: модель в памяти vs store (put/del/CAS), 10⁵ операций.
2. **ENOSPC/EIO** через loop-FS/dm-flakey: нет частичного батча, store read-only, рестарт без ручных шагов.
3. Torn tail в 20 местах → восстановление до последней валидной.
4. Битая середина → fsck FAIL, старт запрещён.
5. Усечение хвоста ниже якоря → FAIL (не torn tail).
6. Подмена `actor`/`ts`/`requestId` → hash FAIL.
7. Два писателя → `EBUSY`.
8. 100 watcher'ов, один завис → остальные живы, завис получает 410.
9. Watch во время 1 000 записей → 0 потерь, 0 дублей.
10. CAS: 50 параллельных update с одним rv → 1×200, 49×409.
11. Restore: снапшот+сегменты+архив на чистый хост → rev/hash совпадают, замер RTO.
12. Golden-векторы JCS (для будущего Rust).
13. Мутанты (≥12): убрать fsync; убрать prev; дубль rev; hash без actor; пропустить anchor; отключить flock; не обновлять committedOffset; разрешить частичный батч; отключить 410; снять лимит строки; отключить authz watch; не писать AUDIT_DENY.

---

## 11. Приёмка (замером)

- SLO из §8 на целевом диске; гистограммы, не средние.
- Drill: kill -9 в середине батча; обрыв питания/VM reset; ENOSPC; порча байта; усечение ниже якоря; restore на чистый хост; замер RTO.
- 1 млн rev: replay/fsck/размер.
- «0 секретов в журнале», «0 пропусков watch», «1×200 при CAS-гонке».

---

## 12. Границы

- Не для data plane (атомы, эмбеддинги, промпты, метрики).
- Один узел в v1; HA — репликация строк журнала позже, за интерфейсом `Store`.
- Не для ручного редактирования; правки только через API.
- При 10⁶+ объектов и высоком RPS — снапшоты/сегменты, затем возможен NATS/etcd за тем же интерфейсом.

---

## 13. Интерфейс

```python
class Store:
    def get(key) -> Record            # + resourceVersion
    def list(prefix, selector=None, limit=None, continue_token=None) -> (items, next)
    def put(key, value, expected_rv=None, request_id=None, dry_run=False) -> Record
    def delete(key, expected_rv=None, request_id=None) -> None
    def watch(from_rev) -> Iterator[Event]   # 410 при отставании
    def snapshot() -> int
    def fsck(repair=False) -> Report
```

Формат журнала — внутреннее дело; замена store на NATS/etcd не меняет API.
