## 0. Правило критериев и как оно проверяется

Каждый критерий приёмки обязан:

1. иметь строку `**Мутант:**` с **глаголом действия** над кодом или данными (добавить, подменить, удалить, смонтировать…). Формулировка «→ падает» без действия недействительна: это исход, а не мутация.
2. быть **исполненным** метамутантом: мутация применяется к коду, целевой тест запускается, и требуется его падение. Неописанный прогон не считается.

**Инструменты (обязательны до отправки на ревью):**

| Инструмент | Что делает | Код отказа |
|---|---|---|
| `tools/crit_lint.py` | статическая проверка документа: мутант есть, описывает действие, нет вакуумной проверки по вертикальной черте, нет ссылок на отсутствующие разделы | 1 |
| `tools/metamutant.py --spec <json>` | применяет мутации к коду и требует падения тестов; выживший мутант = вакуумный критерий | 1 |

**Проверка самих инструментов:** у обоих есть `--selftest`. `metamutant.py --selftest` содержит два мутанта — настоящий (тест обязан упасть) и вакуумный (тест обязан остаться зелёным). Без `pytest` в окружении движок выдаёт SKIP, а не ложный PASS.

**Причина правила — три итерации подряд:**

| Версия | Вакуумный критерий | Почему не мог провалиться |
|---|---|---|
| v0.1 | §9.1 `grep` | вертикальная черта без `-E` — искался литерал |
| v0.2 | §7.3 digest | формула без хешей содержимого |
| v0.3 | §7.3 digest | `len()` не в байтах; каталоги вне digest; мутант на отчёт |

## 2. Принципы

### 2.1 Два разных утверждения о зависимостях

**(а) Нет сетевых и пакетных зависимостей.** Нет `pip install` из сети, нет `ensurepip`, нет `virtualenv`, нет обращений к pypi/зеркалам/реестрам при install и запуске. Отсутствие `pip` в `PATH` — норма.

**(б) Хостовые предпосылки объявлены и проверяются** до создания каталогов:

| Предпосылка | Требование | Проверка | Код |
|---|---|---|---|
| CPython | `>=3.12,<3.13` | `sys.version_info` | 2 |
| архитектура | `x86_64` | `platform.machine()` | 2 |
| glibc | ≥ `min_glibc` из `deps.lock` | `platform.libc_ver()` | 2 |
| системные библиотеки | список из `deps.lock` | `ctypes.util.find_library` | 2 |
| ФС стора | локальная, `flock`, атомарный `rename`, `fsync` | `stat -f` | 8 |
| утилиты | allow-list §2.3 | `doctor` | 2 |

**Мутант [M-2.1-a]:** повысить `min_glibc` в `deps.lock` выше текущей системы → `install` отказывает с кодом 2 до создания каталогов.

**Rust-этап.** Target `x86_64-unknown-linux-musl` сам по себе статику не гарантирует. Проверка: `readelf -d` на артефакте не содержит `NEEDED`, и бинарь запускается на минимальной системе. Это гейт сборки, не приёмочный тест спецификации.

**Мутант [M-2.1-b]:** слинковать артефакт с glibc вместо musl → гейт сборки падает на `readelf -d`.

### 2.2 Целевая платформа — Rust

Переходное правило: Python-поставка ведёт себя так, будто Rust-бинарь уже есть. Нарушения — техдолг D1–D7 (§11) с датами.

**Мутант [M-2.2-a]:** добавить в поставку зависимость, требующую установки из сети → тест §9.6 падает на попытке `connect`.

### 2.3 Allow-list утилит

Разрешено: `systemctl`, `systemctl --user`. Запрещены `cp`, `rsync`, `sha256sum`, `unzip`, `tar`, `chown` (последний — через `os.chown`/`os.lchown`). Всё внутрипроцессно.

**Мутант [M-2.3-a]:** заменить `shutil.copy2` вызовом `cp` → тест `strace -f -e trace=execve` падает.

### 2.4 Барьер `sys.path`

`sys.path` очищается до `lib/nemeq-core` и `lib/pydeps` (через `site.addsitedir`). Импорт не из `lib/` — падение.

**Мутант [M-2.4-a]:** добавить `site-packages` в `sys.path` → тест «враждебный PYTHONPATH» падает.

### 2.5 Поставка зависимостей

Источник истины — `wheelhouse/` + `manifest.sha256`. Поддерживаются только чистые колёса без `*.data/` и без `.pth`. Наличие неподдерживаемого элемента — **отказ до записи** в `lib/pydeps`.

Порядок: сверка sha256 → проверка формата → распаковка с `.dist-info` → сверка `RECORD` по итоговой раскладке → компиляция `.pyc` в `__pycache__` рядом с модулями (§4.3).

### 4.2 Контракт `epishu/<id>/`

Три запрета:

1. **Абсолютные пути внутри данных** — только относительно `<store_root>`; `fsck` находит строки, начинающиеся с `/`.
2. **ФС стора** — NFS/overlay/CIFS не дают гарантий `flock`/`rename`; отказ с кодом 8.

**Мутант [M-4.2-a]:** вписать `/var/nemeq/...` в метаданные атома → `fsck` падает.

### 4.3 Контракт байткода и иммутабельность `lib/`

| Момент | Действие |
|---|---|
| install | `compileall` пишет `.pyc` в `lib/nemeq-core/__pycache__/` и `lib/pydeps/**/__pycache__/` |
| runtime | `PYTHONDONTWRITEBYTECODE=1` во всех шимах; `sys.pycache_prefix` **не задаётся** |

**Threat model назван явно:** `lib/` защищён от **случайной** записи (права `0555` + отсутствие записи байткода + тест). От процесса того же UID `lib/` **не** защищён: владелец снимет права. Реальный барьер — только системный (§6.5), и он best-effort. Обещать защиту от своего UID запрещено этим документом.

**Мутант [M-4.3-a]:** удалить строку `PYTHONDONTWRITEBYTECODE=1` из `bin/nqctl` → тест «в `lib/` не появилось ни одного нового файла после прогона» падает.

**Мутант [M-4.3-b]:** удалить предкомпилированные `.pyc` из поставки → тест «чистый запуск не создаёт файлов в `lib/`» падает (интерпретатор попытается писать байткод).

### 4.4 `var/tmp/` обязателен

Staging в `/tmp` (tmpfs) даст `EXDEV`. `var/tmp/` (0700) — все атомарные записи; `doctor` сверяет `st_dev(var/tmp) == st_dev(var/epishu)`.

**Мутант [M-4.4-a]:** смонтировать `var/tmp` на другую ФС → `doctor` падает.

## 6. Инстансы

### 6.1 Идентичность: `home_id`, `store_id`, `instance_id`

| Поле | Где | Что идентифицирует | Меняется ли |
|---|---|---|---|
| `home_id` | `config/home.toml` | установку (префикс) | только новым install |
| `store_id` | метаданные стора **и** `instance.toml` | **данные стора** | **никогда** (переезжает с данными) |
| `instance_id` | `instance.toml` | конкретный инстанс в префиксе | при каждом `migrate --into-instance` |

`instance.toml` также содержит `lineage: {origin_home_id, origin_instance_id, migrated_at}`.

**Авторитет идентичности — `instance.toml` и метаданные стора, не runtime-файл.** В v0.4 `instance_id` сверялся с `run/instance.json`, которого у нового инстанса нет, а после аварии он может быть протухшим.

Порядок старта:

1. взять лок стора (§6.4). Успешный лок **доказывает**, что живых владельцев нет;
2. сверить `home_id` конфига с `home.toml` → расхождение: код 5;
3. сверить `store_id` `instance.toml` с метаданными стора → расхождение: код 5;
4. при успешном локе любой существующий `run/instance.json` считается **протухшим от мёртвого процесса** и перезаписывается атомарно (tmp+`rename`+`fsync`);
5. `instance_id` в `run/instance.json` — runtime-отражение для клиентов, не источник истины. Расхождение `instance_id` между файлом и `instance.toml` **не** блокирует старт, а перезаписывается.

`/health` отдаёт идентификаторы из памяти живого процесса; проверка «подменили `instance.toml` на диске» отражается на **следующем** старте, а не на каждом запросе — в v0.4 критерий §9.3 требовал перечитывать файл на каждый запрос, что противоречило проверке «при старте».

**Мутант [M-6.1-a]:** подменить `store_id` в `instance.toml` → сервис не стартует с кодом 5.

**Мутант [M-6.1-b]:** подменить `store_id` в одном инстансе → второй продолжает работать (проверка независимости).

**Мутант [M-6.1-c]:** запустить новый инстанс без `run/instance.json` → старт успешен, файл создаётся после лока.

**Мутант [M-6.1-d]:** оставить протухший `run/instance.json` от убитого процесса (`kill -9`) → следующий старт успешен, файл перезаписан.

**Мутант [M-6.1-e]:** подменить `instance_id` только в `run/instance.json` → старт успешен, файл перезаписан из `instance.toml`.

### 6.3 Жизненный цикл

**Мутант [M-6.3-a]:** вызвать `destroy` при живом сервисе → код 4.

**Мутант [M-6.3-b]:** удалить lock-файл в конце `destroy` → тест «конкурентный старт после destroy» падает (два владельца).

### 6.4 Lock живёт рядом со стором (закрывает B1)

В v0.3 лок лежал в `<store>/lock`, из-за чего: digest зависел от pid внутри лока, лок копировался при миграции, после `rename` flock оставался на отсоединённом inode, а `destroy` с удалением файла давал unlink-lockfile race.

**Нормативно — канонический путь лока:**

```
<dirname(realpath(store))>/.nemeq-store.<sha256(realpath(store))[:16]>.lock
open(O_RDWR|O_CREAT|O_NOFOLLOW, 0600)
flock(LOCK_EX|LOCK_NB)
```

Свойства, которые это обеспечивает (каждое — отдельным мутантом):

- **один store — один lock**: путь зависит только от `realpath(store)`, не от имени инстанса и не от того, каким именем store открыли;
- **разные store в одном каталоге — разные lock**: хеш различает их;
- **лок вне `store/`**: не попадает в `store_digest` и не копируется при миграции;
- **лок внутри `var/`**: при дефолтной раскладке путь `var/store` даёт лок `var/.nemeq-store.<hash>.lock`, то есть он остаётся внутри `ReadWritePaths=.../var` из §6.5 — важно, иначе systemd с `ProtectSystem=strict` упадёт с `EROFS`;
- **read-only ФС**: операции, которым нужен lock, на read-only сторе **запрещены** (код 8). Для `fsck`/`verify` без записи предусмотрен `--read-only --no-lock`, который явно не берёт лок и печатает предупреждение в отчёт;
- **жизненный цикл**: lock не удаляется на `destroy` и не переносится при `migrate` — это гарантирует отсутствие unlink-lockfile race. `uninstall --purge` удаляет **всё дерево** `$NEMEQ_HOME` целиком, включая лок-файлы, предварительно проверив, что живых владельцев нет (попытка взять лок + проверка pid);
- при удержании — сообщение `store busy: pid N`, код 4.

**Мутант [M-6.4-a]:** перенести lock внутрь `var/store/` → тест «digest до/под/после лока совпадает» падает.

**Мутант [M-6.4-b]:** добавить `unlink(lock)` в `destroy` → тест «destroy + конкурентный старт» падает (два владельца).

**Мутант [M-6.4-c]:** запустить два инстанса с разными именами и одним `--store` → второй падает с кодом 4.

**Мутант [M-6.4-d]:** открыть один store двумя разными путями (через симлинк на каталог) → оба процесса получают лок на один store, тест «два имени одного store блокируются» падает.

**Мутант [M-6.4-e]:** создать два разных store в одном каталоге → тест «оба живы одновременно» падает, если хеш не различает пути.

**Мутант [M-6.4-f]:** запустить сервис через user-unit с `ProtectSystem=strict` и `ReadWritePaths=.../var` → падает с `EROFS` на локе, если лок оказался вне `var/`.

**Мутант [M-6.4-g]:** выполнить `uninstall --purge` при живом владельце → код 4, дерево не удалено.

### 6.5 systemd — best-effort песочница

Дефолт — user-unit `~/.config/systemd/user/nemeq-<instance>.service`. Системные unit — уровень (в). Абсолютный путь прописывает `nqctl install-unit`; `%h` запрещён.

**Формулировка понижена до best-effort** (в v0.3 обещала больше, чем даёт user-unit): `ProtectSystem=strict` и `ReadOnlyPaths` применяются только при доступных unprivileged user namespaces; если их нет, systemd применяет unit **без** песочницы.

Шаблон:

```
Environment=NEMEQ_HOME=<abs>
Environment=NEMEQ_INSTANCE=<name>
ExecStart=<abs>/bin/nqctl serve
Restart=on-failure
KillMode=mixed
TimeoutStopSec=20
NoNewPrivileges=yes
PrivateTmp=yes
ProtectSystem=strict
ReadWritePaths=<abs>/instances/<name>/var
ReadWritePaths=<abs>/instances/<name>/logs
ReadWritePaths=<abs>/instances/<name>/run
ReadOnlyPaths=<abs>/lib
```

**Runtime-самопроверка:** `serve` на старте читает `/proc/self/status` (`NoNewPrivs`) и `/proc/self/mountinfo` (ro-монтирование `lib`) и записывает фактические значения в `run/instance.json → sandbox`. `doctor --hardened` требует их наличия; без них сервис помечает себя `sandbox: false` и продолжает.

`install-unit` берёт пути из `nqctl env --json`. Если фактический `store_realpath` не совпадает с юнитом — отказ при старте с текстом «regenerate unit».

**Lingering:** по умолчанию сервис живёт, пока активна сессия пользователя. Работа после logout и на загрузке требует `loginctl enable-linger <user>` — отдельное действие с привилегией.

**Мутант [M-6.5-a]:** вставить `%h` в шаблон юнита → тест `grep -c '%h'` падает.

**Мутант [M-6.5-b]:** расширить `ReadWritePaths` на весь префикс → тест «процесс не может писать в lib» падает.

**Мутант [M-6.5-c]:** отключить `enable-linger` в фикстуре → тест «сервис поднимается после logout» падает.

### 7.1 Предусловия и лок

- target непуст → код 2 (флага слияния нет, §7.6);

### 7.2 Crash-safe состояние (закрывает B2)

`run/migration.json` + `fsync` файла и каталога `run/` на каждом переходе.

| Состояние | Сделано | Повторный запуск |
|---|---|---|
| `prepared` | маркер записан и `fsync`, staging создан | удаляет staging, начинает заново (или `--continue`) |
| `copying` | идёт копирование | `--continue` дописывает по манифесту |
| `verifying` | копия готова, идёт fsck+digest | повторяет проверку |
| **`publishing`** | intent записан и `fsync` **до** `rename` | см. правило ниже |
| `published` | `rename` выполнен | дописывает отчёт |
| `reported` | отчёт записан | ничего, успех |
| `failed:<reason>` | ошибка | печатает причину, требует `--restart` |

**Правило восстановления `publishing` — все комбинации (в v0.4 их было три, «нет обоих» не покрывалось):**

| `var` | staging | манифест | Решение |
|---|---|---|---|
| есть | нет | совпал, и digest `var` = ожидаемому | считать опубликованным, дописать отчёт |
| есть | нет | **не совпал** | код 10, состояние `failed:corrupt_publish`, ничего не удалять |
| нет | есть | — | вернуться в `verifying` |
| есть | есть | — | код 11, ручное разбирательство, ничего не удалять |
| нет | нет | — | код 11, состояние `failed:lost`, требуется `--restart` с нуля |

«Манифест совпал» означает: ожидаемый `store_digest` пересчитан по фактическому дереву `var` **и совпал** с зафиксированным до публикации. Проверять только наличие файла манифеста недостаточно: он может уцелеть при повреждённых данных.

Состояние `copying` фиксируется и `fsync` **до** первого байта копирования, иначе краш в начале копирования оставит `prepared` без понимания, начиналось ли копирование.

**Пока состояние миграции не разрешено (`reported` или явный откат), сервис не стартует** (код 11) — иначе опубликуется непроверенное дерево.

**Манифест и его digest лежат в `run/`, не в staging** — иначе после `rename` посторонний файл окажется в корне `var/` и strict-`fsck` опубликованного стора упадёт.

**Порядок (нормативный):**

1. взять лок источника и target;
2. сравнить `st_dev(staging_parent)` с `st_dev(dirname(target_var))` — до создания `target_var`;
3. записать `prepared` + `fsync` файла + `fsync` каталога `run/`;
4. создать `var.migrating-<ts>/`;
5. копировать пофайлово (кроме `<var>.lock`); затем `fsync` всех файлов и каталогов staging;
6. `verifying`: `fsck` strict + сравнение `store_digest` источник↔staging;
7. `chown` по режиму §7.4; повторный `fsync`;
8. записать `publishing` + `fsync`;
9. `rename(staging → var)`; `fsync` родительского каталога;
10. `published`; записать отчёт в `run/migration-report.json` + `fsync`;
11. `reported`; отпустить локи.

**Мутант [M-7.2-a]:** прервать процесс (`kill -9`) между шагами 9 и 10 → повторный запуск дописывает отчёт, `var` остаётся опубликованным и `fsck`-чистым.

**Мутант [M-7.2-b]:** прервать между шагами 8 и 9 → повторный запуск возвращается в `verifying`, публикации не происходит.

### 7.3 `store_digest` — по содержимому, с каталогами (закрывает B3)

В v0.3 длина не была в байтах, каталоги были вне digest, а режимы не покрывались.

Каноническое кодирование. **Длина — всегда в байтах UTF-8**, сортировка — по байтам:

```
для каждого relpath (относительный, UTF-8, NFC) в порядке байтового возрастания:
    u64be(len_utf8(relpath)) || relpath || u8(kind)
    kind=0 (file):    u64be(size) || sha256(content) || u32be(mode & 0o7777)
    kind=1 (symlink): u64be(len_utf8(target)) || target
    kind=2 (dir):     (тело отсутствует)

store_digest = "sha256:" + sha256(D)
```

**Единый физический корень digest — `<var>`, не `<store>`.** В v0.4 было написано «под `<store>` (`store/`, `epishu/`, `state/`…)», хотя `epishu/` и `state/` лежат рядом со `store/`, а не внутри. Корень — `<var>`:

- обходятся все файлы и **все каталоги** под `<var>`, **кроме** `var/tmp/` (staging, изменчив) и lock-файлов `var/.nemeq-store.*.lock`;
- корневая директория `<var>` **входит** в набор записью `kind=2` с пустым relpath — иначе пустой стор и стор с одним пустым каталогом неразличимы;
- **режим каталогов хешируется** так же, как у файлов (`u32be(mode & 0o7777)` в записи `kind=2`);
- **имена — сырые байты**: `relpath` кодируется через `os.fsencode`, без UTF-8-перекодирования. Имя, не декодируемое как UTF-8, обрабатывается побайтово и **не роняет** digest;
- **Unicode-правило:** отвергается имя, у которого `NFC(name) != name` (то есть имя уже не в NFC-форме). Сравнение `NFC != NFD` из v0.4 было неверным: оно отвергало обычные NFC-имена с диакритикой. Отказ — код 2 при `install` и код 7 при `migrate`; проверка выполняется в **обоих** путях, а не только в `install`;
- неподдерживаемые типы файлов (fifo, socket, device) → код 7 с перечнем;
- sampling **запрещён**. Ускорение — только Merkle с сохранением полноты, отдельным решением.

**Мутант [M-7.3-a]:** удалить пустой каталог `epishu/<id>/wal/` из staging → digest расходится, шаг 6 даёт код 10.

**Мутант [M-7.3-b]:** подменить один байт в файле каждого класса (`atoms`, `view`, `paqidutu`, `wal`, `anchor`, `state`, `data`) → digest меняется в каждом случае.

**Мутант [M-7.3-c]:** сменить режим файла `0644 → 0777` → digest меняется.

**Мутант [M-7.3-d]:** переставить порядок обхода → digest не меняется (тест на стабильность).

**Мутант [M-7.3-e]:** создать пустой стор и стор с одним пустым каталогом → digest различается (в v0.4 различие терялось).

**Мутант [M-7.3-f]:** изменить режим каталога `0755 → 0700` → digest меняется.

**Мутант [M-7.3-g]:** создать файл с именем в NFD-форме (`e` + U+0301) → `install` отказывает с кодом 2, `migrate` — с кодом 7.

**Мутант [M-7.3-h]:** создать файл с именем, не декодируемым как UTF-8 (сырые байты `\xff`) → digest считается без исключения, имя учтено побайтово.

### 7.4 Режимы миграции (закрывает B4)

В v0.3 `chown` требовал root, что противоречило allow-list, а rootless был невыполним для типового root-стора.

**Множество допустимых владельцев источника.** В v0.4 режимы были взаимоисключающими и не покрывали типовой гибрид «каталог root, рабочие сегменты — сервисный uid».

| Режим | Допустимые UID источника | Требования |
|---|---|---|
| **rootless** | ровно `{target}` | запуск от целевого пользователя |
| **root-assisted** | `{0, target}` | root + явно `--root-assisted --target-uid N --target-gid N` |
| **root-assisted + adopt** | `{0, target} ∪ adopt_uids` | то же + `--adopt-uid U1[,U2...]` |

`--adopt-uid` **расширяет** множество допустимых исходных UID; он не задаёт целевой uid (целевой — всегда `--target-uid`). Любой файл с uid вне разрешённого множества → **код 14 до начала копирования** (preflight-скан по всему дереву, а не по первому встреченному).

**Порядок прав и digest (закрывает B6).** В v0.4 сравнение digest шло до `chown`, а digest включает режим — значит после `chown` опубликованный стор уже не соответствовал проверенному.

Нормативный порядок:

1. скопировать данные в staging (права — как в источнике, `chown` ещё не делался);
2. `fsync` всех файлов и каталогов staging;
3. **нормализовать права в staging** по §4.7 (`0700` каталоги, `0600` файлы, снять setuid/setgid);
4. `os.lchown`/`os.chown` (без exec) на `--target-uid:--target-gid`, **включая** `run/migration*.json`;
5. **только теперь** вычислить `store_digest` staging и сравнить с ожидаемым digest источника, нормализованным по той же функции (одна спецификация нормализации для обеих сторон);
6. `rename` в `var/` и финальная сверка digest **опубликованного** дерева с ожидаемым — до записи `published`.

Сравниваются две величины: digest **содержимого** (данные + пути + типы) и digest **метаданных** (режимы + владелец). Расхождение содержимого — код 10; расхождение метаданных — код 10 с пометкой `metadata`, в отчёт пишется таблица «источник → цель» по правам.

- запуск от root **без** явного флага → код 2 (привилегия не применяется молча);
- `--target-uid 0` запрещён;
- проверка `--target-uid == st_uid($NEMEQ_HOME/config/home.toml)` — иначе код 2;
- `chown` распространяется и на `run/migration*.json`;
- файлы третьих uid без `--adopt-uid` → код 14 с перечнем.

**Мутант [M-7.4-a]:** запустить миграцию root-стора без `--root-assisted` → код 2.

**Мутант [M-7.4-b]:** запустить root-assisted с `--target-uid 0` → код 2.

**Мутант [M-7.4-c]:** оставить `run/migration.json` с владельцем root после root-assisted → тест «все файлы HOME принадлежат целевому uid» падает.

**Мутант [M-7.4-d]:** выполнить `chown` после сравнения digest (как в v0.4) → тест «digest опубликованного дерева = ожидаемому» падает.

**Мутант [M-7.4-e]:** создать в источнике файл `0644` → после нормализации в `0600` digest метаданных расходится с источником; тест требует, чтобы это было отражено как разрешённое преобразование, а не как ошибка.

## 9. Критерии приёмки

### 9.1 Ни одного пути ОС в любом файле

В v0.3 проверялись только `*.py`, `*.rs`, `*.sh`, `*.toml`, `*.service` — это deny-list, который всегда неполон.

Инвертированный тест: сканируются **все** файлы репозитория, allow-list исключений явный.

```sh
rg -a --hidden --no-ignore -g '!.git' -n \
  -e '/(var|var/lib|opt|usr/local|etc|srv|tmp)/nemeq' \
  -e '%[tSCEL]/nemeq' -e '\.nq\b' \
  --glob '!massaru/legacy.py' --glob '!docs/**' --glob '!tests/fixtures/**'
```

**Три дополнительных проверки, которых не было в v0.4:**

1. **`--no-ignore`** — иначе `.gitignore`/`.rgignore` скрывают часть файлов, и тест их не видит.
2. **AST-проверка конкатенации.** Регулярка не поймает `Path("/var") / "nemeq"` или `os.path.join("/var", "nemeq")`. Отдельный тест парсит все `*.py` через `ast` и падает, если строковый литерал `/var`, `/opt`, `/etc`, `/run` встречается вне `massaru/legacy.py`.
3. **Содержимое wheel-архивов.** `rg -a` не заглядывает в сжатые deflate-потоки внутри `.whl`. Отдельный тест распаковывает каждый архив `wheelhouse/*.whl` во временный каталог и прогоняет тот же паттерн по содержимому.

Плюс тест: каждый legacy-путь из §4.1 имеет строку в таблице §4.1.

**Мутант [M-9.1-a]:** добавить `/var/nemeq` в шаблон `.j2`, в `bin/`-скрипт без расширения и в `.yml` → тест падает в каждом случае.

**Мутант [M-9.1-b]:** вписать `Path("/var") / "nemeq"` в `nqctl/cli.py` → AST-тест падает, регулярка при этом молчит.

**Мутант [M-9.1-c]:** добавить файл в `.gitignore`, содержащий `/var/nemeq`, → тест с `--no-ignore` падает, без него — молчал бы.

**Мутант [M-9.1-d]:** положить в `wheelhouse/*.whl` модуль со строкой `/var/nemeq` → тест содержимого архивов падает.

**Мутант [M-9.1-e]:** вписать `%t/nemeq` в unit-шаблон → тест падает на паттерне спецификаторов systemd.

**Мутант [M-9.1-f]:** удалить строку `/var/lib/nemeq` из таблицы §4.1 → тест соответствия падает.

### 9.10 Инструменты критериев проверены

Три требования, каждое закрывает найденную в v0.4 дыру:

1. **`metamutant.py --selftest`** проходит в CI.
2. **SKIP — это отказ, а не успех.** В v0.4 отсутствие `pytest` давало код 0, и CI считал шаг зелёным. Теперь `selftest` при недоступном `pytest` возвращает **код 3**, а `--spec` — **код 2**. Ложнозелёный прогон без рабочей среды невозможен.
3. **Сверка покрытия `--coverage`.** В v0.4 документ мог содержать 45 мутантов, а `spec.json` — 2, и оба инструмента рапортовали успех. Теперь у каждого мутанта в документе есть ID вида `M-раздел-буква`, а `metamutant.py --coverage <док> --spec <json>` падает с кодом 1, если хотя бы один ID документа отсутствует в spec (или наоборот).

**Нумерация мутантов.** Каждый мутант в этом документе помечен ID `[M-<раздел>-<буква>]`. ID стабильны и не переиспользуются.

**Мутант [M-9.10-a]:** сломать `crit_lint` так, чтобы он не находил отсутствующий мутант → его собственная фикстура падает.

**Мутант [M-9.10-b]:** убрать из `metamutant` различение инфраструктурного падения → selftest падает на вакуумном мутанте.

**Мутант [M-9.10-c]:** вернуть `return 0` вместо `return 3` в ветке SKIP → selftest в среде без pytest даёт зелёный, тест «SKIP = отказ» падает.

## 11. Решения по ранее открытым вопросам (нормативно)

В v0.4 эти вопросы были открыты; оба ревьюера указали, что оставлять их перед кодом нельзя. Решения приняты:

1. **`--adopt-uid`** — достаточно явного CLI-флага. `home.toml` не засоряется миграционной историей; факт пишется в `lineage` и `migration-report.json`.
2. **Merkle** — строго после замера полного линейного digest на 1M rev. Преждевременная оптимизация канонического формата создаёт риск новых коллизий.
3. **`--verify-target`** — только read-only: `/health` + `fsck` + read-запрос, либо прогон на временной копии. **Менять `rev` целевого стора при миграции запрещено**: это нарушит равенство digest и `last_hash` между источником и целью.
4. **`doctor --hardened`** — опциональный профиль. Обязательным его делать нельзя: приёмка упала бы на стандартных Ubuntu 24.04 и контейнерных раннерах с ограниченными unprivileged userns, что противоречит best-effort формулировке §6.5. В CI гоняются оба режима разными джобами.
5. **NFC/NFD** — отвергать имя, у которого `NFC(name) != name`, в `install` (код 2) и в `migrate` (код 7). Молчаливая нормализация меняет байты путей, ломает относительные симлинки и создаёт риск перезаписи при коллизии.
