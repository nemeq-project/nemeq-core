# TEXTSTORE v0.1 (заменён v0.2)

> **Внимание:** после челленджа 9 ревьюеров — см. `TEXTSTORE_v0.2.md`. — подсистема хранения на текстовых файлах

**Дата:** 2026-11-24 · **Статус:** проект (заменяет LMDB-решение в APISERVER v0.3) · **Владелец:** Верста
**Идея:** источник истины — append-only журнал JSONL; состояние — материализация; человеческие представления — MD/CSV. Ноль зависимостей, audit by construction.

---

## 1. Почему текстовый журнал

- **Ноль зависимостей:** нет БД, демона, бинарного формата.
- **Audit by construction:** каждая строка — транзакция с hash-chain; журнал и есть аудит.
- **Читаемо и диффаемо:** `grep`, `jq`, `git diff`; инцидент разбирается без спец-инструментов.
- **Бэкап = файлы:** копия каталога; restore-drill тривиален.
- **Контроль:** мы владеем семантикой durability, а не гадаем, что делает чужой движок.

Цена: ~500–700 строк кода + тесты на частичные записи, восстановление и компакцию. Это осознанный обмен: код вместо зависимости.

## 2. Формат

```
/var/lib/nemeq/apiserver/
├── lock                     # flock: один писатель
├── log/
│   ├── 000001.jsonl         # сегменты по 64 МБ
│   └── 000002.jsonl
├── snap/
│   ├── 0001000.json         # снапшот состояния на ревизии
│   └── 0002000.json
├── state/                   # материализация (НЕ истина)
│   ├── epishu/octavia.json
│   └── session/octavia-1.json
├── views/                   # человеческие представления (генерятся)
│   ├── index.md
│   └── audit.csv
└── meta.json                # текущая rev, last_hash, версия формата
```

### 2.1. Запись журнала (одна строка = одна транзакция)

```json
{"rev":1235,"prev":"sha256:...","ts":"2026-11-24T10:00:00Z","actor":"versta",
 "requestId":"...","txn":[
   {"op":"put","key":"epishu/octavia","value":{"spec":{...},"status":{...},"uid":"..."}}
 ],
 "hash":"sha256:..."}
```

- `hash = sha256(canonical(rev, prev, txn))`; `canonical` — JSON с сортировкой ключей и без пробелов.
- `prev` — `hash` предыдущей строки → глобальная цепочка.
- Несколько `op` в одной строке = атомарная транзакция (replay применяет целиком или никак).

### 2.2. Почему JSONL, а не CSV/MD как истина

| Формат | Годится как истина? | Почему |
|---|---|---|
| JSONL | **да** | одна строка = одна транзакция, вложенность, канонизация, hash, append |
| CSV | нет | нет вложенности, экранирование, нет транзакций; годится для audit-выгрузки |
| Markdown | нет | человекочитаемо, но парсинг неоднозначен; годится для манифестов/просмотра |
| YAML | нет | тот же парсинг + неоднозначности; допустим как вход `nqctl apply` |

MD/CSV генерируются из состояния: люди читают, машина не доверяет.

## 3. Путь записи и инварианты

1. **Один писатель.** `flock` на `lock`; второй процесс падает с `EBUSY` (не ждёт).
2. **Транзакция:** собрать `txn`, прочитать текущую `rev`/`last_hash` из памяти, проверить CAS (`expectedRev`), сформировать запись.
3. **Group commit:** писать батч (2–10 мс окно), затем один `fsync` на батч. Ответ клиенту — после fsync.
4. **Ответ 200 только после fsync.** Ошибка fsync → 500, `rev` не двигается, клиент повторяет.
5. **Монотонность:** `rev` не переиспользуется; удаление — `op:"del"` + tombstone, не вырезание строки.
6. **Идемпотентность:** повтор `put` с тем же `requestId` → 200 и та же запись (dedup по `requestId` в окне 24 ч); create по существующему ключу → 409.
7. **Секреты:** в журнал не попадают; только `secretRef`.

### 3.1. Замер (этот хост, ext4/LVM, 24.11.2026)

| batch | ops/s | commits/s | размер |
|---:|---:|---:|---:|
| 1 | **20** | 20 | 1,33 МБ / 5 000 записей |
| 10 | 191 | 19 | — |
| 100 | **1 922** | 19 | — |
| 1 000 | 12 662 | 13 | — |
| raw fsync (4 КБ) | — | **47,5 мс** | — |

**Вывод:** физика диска доминирует; текст не тормозит. Group commit обязателен. 5 000 записей = 1,33 МБ (~266 Б/запись); 1 млн ≈ 266 МБ до компакции.

## 4. Восстановление и fsck

| Сбой | Поведение |
|---|---|
| Оборванная последняя строка (power loss) | replay останавливается на последней валидной; `--repair` обрезает хвост до неё (замер: 5 000/5 000 восстановлено, обрезано 37 Б) |
| Битая строка в середине | replay останавливается, `fsck` показывает первую плохую `rev`; автопродолжение запрещено — restore из бэкапа или явное усечение с подтверждением |
| Разрыв hash-chain | `fsck` → FAIL, старт запрещён |
| Дубли `rev` | `fsck` → FAIL |
| Два писателя | второй не стартует (`flock`) |
| Диск полон | запись отклоняется до fsync, 507; `rev` не двигается |

`nqctl store fsck [--repair]`, `nqctl store verify`, `nqctl store snapshot`.

---

## 5. Снапшоты и компакция

- Снапшот каждые 1 000 ревизий или 5 минут: `snap/<rev>.json` = `{rev, hash, state}`.
- Запись снапшота: temp → `fsync` → `rename` → `fsync(dir)`; храним 2 последних.
- Компакция: после снапшота ротация сегмента; старые сегменты **не удаляем** без бэкапа (аудит).
- Restore: проверить снапшот → replay сегменты после `rev` → сверить `hash`/`rev`.

---

## 6. Watch

- Подписка `fromRev`: сначала читаем журнал с диска, потом live-очередь в процессе.
- Разрыв/отставание: relist из снапшота + replay; bookmarks каждые 100 ревизий.
- Читатели не блокируют писателя (append-only).

## 7. Матрица отказов и меры

| Риск | Мера |
|---|---|
| Свой код durability | тесты: crash на каждом шаге, torn tail fuzz, hash-chain, restore-drill |
| Середина журнала битая | fsync, бэкапы, `fsck`, снапшоты; усечение только с подтверждением |
| Рост файла | сегменты 64 МБ, снапшоты, архивирование, не удалять без копии |
| Ручная правка | `chmod 0700`, `flock`, `fsck` при старте; правки только через API |
| Медленный fsync | group commit; `sync=False` запрещён |
| Один узел | running epishu живут без apiserver; RTO ≤15 мин; HA позже репликацией строк |
| Утечка секретов | redaction, `secretRef`, тест «0 секретов в журнале» |

## 8. Тесты (обязательные)

1. property-based: модель в памяти vs store на случайных транзакциях (put/del/CAS), 10⁵ операций.
2. crash-инъекции: обрыв после write / после fsync / между сегментами; после рестарта — целостность.
3. torn tail: обрезать строку в N местах → восстановление до последней валидной.
4. битый байт в середине → fsck FAIL, старт запрещён.
5. два писателя → второй `EBUSY`.
6. restore: снапшот + сегменты → состояние и `rev` совпадают.
7. мутанты: убрать fsync; убрать проверку `prev`; разрешить дубль `rev`; пропустить hash; не обновить `meta` — каждый должен ловиться.
8. нагрузка: 10⁵ записей, замер replay/snapshot/p99.

---

## 9. Границы

- **Не для данных:** атомы памяти, эмбеддинги, промпты, метрики — вне (data plane).
- **Не для мульти-узла в v1:** один писатель; HA — репликация журнала позже.
- **Не для миллионов мелких объектов:** при 10⁶+ записей и высоком RPS — снапшоты + сегменты, затем возможен переход на NATS/etcd за тем же `Store`.
- **Не для ручного редактирования:** журнал только append через API.

## 10. Интерфейс

```python
class Store:
    def get(key) -> Record
    def list(prefix, label_selector=None) -> list[Record]
    def put(key, value, expected_rev=None, request_id=None) -> Record
    def delete(key, expected_rev=None, request_id=None) -> None
    def watch(from_rev) -> Iterator[Event]
    def snapshot() -> int
    def fsck(repair=False) -> Report
```

Наружу — только этот интерфейс; формат журнала — внутреннее дело. Замена на NATS/etcd не меняет API.
