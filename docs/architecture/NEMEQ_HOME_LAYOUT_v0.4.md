## 0. Правило критериев и как оно проверяется

Каждый критерий приёмки обязан:

1. иметь строку `**Мутант:**` с **глаголом действия** над кодом или данными (добавить, подменить, удалить, смонтировать…). Формулировка «→ падает» без действия недействительна: это исход, а не мутация.
2. быть **исполненным** метамутантом: мутация применяется к коду, целевой тест запускается, и требуется его падение. Неописанный прогон не считается.

**Инструменты (обязательны до отправки на ревью):**

| Инструмент | Что делает | Код отказа |
|---|---|---|
| `tools/crit_lint.py` | статическая проверка документа: мутант есть, описывает действие, нет вакуумной проверки по вертикальной черте, нет ссылок на отсутствующие разделы | 1 |
| `tools/metamutant.py --spec <json>` | применяет мутации к коду и требует падения тестов; выживший мутант = вакуумный критерий | 1 |

**Проверка самих инструментов:** у обоих есть `--selftest`. `metamutant.py --selftest` содержит два мутанта — настоящий (тест обязан упасть) и вакуумный (тест обязан остаться зелёным). Без `pytest` в окружении движок выдаёт SKIP, а не ложный PASS.

**Причина правила — три итерации подряд:**

| Версия | Вакуумный критерий | Почему не мог провалиться |
|---|---|---|
| v0.1 | §9.1 `grep` | вертикальная черта без `-E` — искался литерал |
| v0.2 | §7.3 digest | формула без хешей содержимого |
| v0.3 | §7.3 digest | `len()` не в байтах; каталоги вне digest; мутант на отчёт |

## 2. Принципы

### 2.1 Два разных утверждения о зависимостях

**(а) Нет сетевых и пакетных зависимостей.** Нет `pip install` из сети, нет `ensurepip`, нет `virtualenv`, нет обращений к pypi/зеркалам/реестрам при install и запуске. Отсутствие `pip` в `PATH` — норма.

**(б) Хостовые предпосылки объявлены и проверяются** до создания каталогов:

| Предпосылка | Требование | Проверка | Код |
|---|---|---|---|
| CPython | `>=3.12,<3.13` | `sys.version_info` | 2 |
| архитектура | `x86_64` | `platform.machine()` | 2 |
| glibc | ≥ `min_glibc` из `deps.lock` | `platform.libc_ver()` | 2 |
| системные библиотеки | список из `deps.lock` | `ctypes.util.find_library` | 2 |
| ФС стора | локальная, `flock`, атомарный `rename`, `fsync` | `stat -f` | 8 |
| утилиты | allow-list §2.3 | `doctor` | 2 |

**Мутант:** повысить `min_glibc` в `deps.lock` выше текущей системы → `install` отказывает с кодом 2 до создания каталогов.

**Rust-этап.** Target `x86_64-unknown-linux-musl` сам по себе статику не гарантирует. Проверка: `readelf -d` на артефакте не содержит `NEEDED`, и бинарь запускается на минимальной системе. Это гейт сборки, не приёмочный тест спецификации.

**Мутант:** слинковать артефакт с glibc вместо musl → гейт сборки падает на `readelf -d`.

### 2.2 Целевая платформа — Rust

Переходное правило: Python-поставка ведёт себя так, будто Rust-бинарь уже есть. Нарушения — техдолг D1–D7 (§11) с датами.

**Мутант:** добавить в поставку зависимость, требующую установки из сети → тест §9.6 падает на попытке `connect`.

### 2.3 Allow-list утилит

Разрешено: `systemctl`, `systemctl --user`. Запрещены `cp`, `rsync`, `sha256sum`, `unzip`, `tar`, `chown` (последний — через `os.chown`/`os.lchown`). Всё внутрипроцессно.

**Мутант:** заменить `shutil.copy2` вызовом `cp` → тест `strace -f -e trace=execve` падает.

### 2.4 Барьер `sys.path`

`sys.path` очищается до `lib/nemeq-core` и `lib/pydeps` (через `site.addsitedir`). Импорт не из `lib/` — падение.

**Мутант:** добавить `site-packages` в `sys.path` → тест «враждебный PYTHONPATH» падает.

### 2.5 Поставка зависимостей

Источник истины — `wheelhouse/` + `manifest.sha256`. Поддерживаются только чистые колёса без `*.data/` и без `.pth`. Наличие неподдерживаемого элемента — **отказ до записи** в `lib/pydeps`.

Порядок: сверка sha256 → проверка формата → распаковка с `.dist-info` → сверка `RECORD` по итоговой раскладке → компиляция `.pyc` в `__pycache__` рядом с модулями (§4.3).

**Мутант:** подменить байт в колесе → `deps install` отказывает с кодом 9. Добавить `.pth` в колесо → отказ до записи.

## 4. Раскладка

```
$NEMEQ_HOME/                          # префикс (~/.nemeq)
├── config/home.toml                  # home_id, layout_version        ← ПРЕФИКС
├── bin/                              # шимы
├── lib/                              # immutable: nemeq-core/, pydeps/, INSTALL.json
└── instances/<name>/
    ├── config/instance.toml          # instance_id, schema_version, port, store_path  ← ИНСТАНС
    ├── var/                          # mutable-корень
    │   ├── store/                    # данные; лок РЯДОМ, не внутри (§7.1)
    │   ├── epishu/<id>/
    │   ├── state/
    │   ├── data/
    │   └── tmp/
    ├── logs/
    └── run/                          # pid, instance.json, migration.json, migration-report.json
```

### 4.1 Полная таблица преобразования (включая `/var/lib/nemeq`)

| Источник (legacy) | Цель | Тип |
|---|---|---|
| `/var/nemeq/apiserver/` | `<inst>/var/store/` | **переименование** |
| `/var/nemeq/epishu/` | `<inst>/var/epishu/` | 1:1 |
| `/var/nemeq/state/` | `<inst>/var/state/` | 1:1 |
| `/var/nemeq/data/` | `<inst>/var/data/` | 1:1 |
| `/var/lib/nemeq/` | `<inst>/var/store/` (если `apiserver` нет) | **переименование** |
| `/var/nemeq/` (прочее) | — | **нет правила → код 7** |
| `/opt/nemeq/` | `$NEMEQ_HOME/lib/` | immutable |
| `/run/nemeq/` | `<inst>/run/` | не переносится |

Конфликт `/var/lib/nemeq` и `/var/nemeq/apiserver` одновременно → код 7 с указанием обоих путей.

**Уровень вложенности:** всё внутри `epishu/<id>/` (`wal/`, `atoms/`, `traces/`, `state/`, `view/`, `paqidutu/`, `zikru-zi/`, `zikru-su/`, `raw/`, `archive/`, `observability_log/`) остаётся внутри каждого `epishu/<id>/` без изменения уровня.

**Мутант:** добавить в источник файл вне таблицы → `migrate` отказывает с кодом 7 и именем файла.

**Мутант:** создать оба legacy-пути стора (`/var/lib/nemeq` и `/var/nemeq/apiserver`) → `migrate` отказывает с кодом 7.

### 4.2 Контракт `epishu/<id>/`

Три запрета:

1. **Абсолютные пути внутри данных** — только относительно `<store_root>`; `fsck` находит строки, начинающиеся с `/`.
2. **ФС стора** — NFS/overlay/CIFS не дают гарантий `flock`/`rename`; отказ с кодом 8.
3. **Глубина вложенности** — пути только через резолверы.

**Мутант:** вписать `/var/nemeq/...` в метаданные атома → `fsck` падает.

### 4.3 Контракт байткода и иммутабельность `lib/`

| Момент | Действие |
|---|---|
| install | `compileall` пишет `.pyc` в `lib/nemeq-core/__pycache__/` и `lib/pydeps/**/__pycache__/` |
| runtime | `PYTHONDONTWRITEBYTECODE=1` во всех шимах; `sys.pycache_prefix` **не задаётся** |

**Threat model назван явно:** `lib/` защищён от **случайной** записи (права `0555` + отсутствие записи байткода + тест). От процесса того же UID `lib/` **не** защищён: владелец снимет права. Реальный барьер — только системный (§6.5), и он best-effort. Обещать защиту от своего UID запрещено этим документом.

**Мутант:** снять `PYTHONDONTWRITEBYTECODE` в шиме → тест «lib не изменился после прогона» падает (появляется `__pycache__`).

### 4.4 `var/tmp/` обязателен

Staging в `/tmp` (tmpfs) даст `EXDEV`. `var/tmp/` (0700) — все атомарные записи; `doctor` сверяет `st_dev(var/tmp) == st_dev(var/epishu)`.

**Мутант:** смонтировать `var/tmp` на другую ФС → `doctor` падает.

### 4.5 Манифест установки

`lib/INSTALL.json`: `layout_version`, `nemeq_version`, `schema_version`, `platform_tag`, `deps_lock_sha256`, `min_glibc`, `build_id`, `installed_at`.

**Мутант:** увеличить `schema_version` в `instance.toml` на 1 → сервис не стартует, сообщение «store schema N > supported M».

### 4.6 Сокеты и длина пути

`sun_path` — 108 байт. Валидация в `install`/`doctor`, порог 100; для длинных HOME — `var/run-short` (0700) или abstract sockets.

**Мутант:** изменить `HOME` на строку длиной 120 символов → `doctor` падает до старта (валидация длины пути).

### 4.7 Квоты и права

`0700` на `var/`, `0600` на файлы и `instance.toml`, umask `077`. `max_state_bytes` + soft-лимит 80 % в лог. `doctor` проверяет права, место, UID.

**Мутант:** выставить umask 000 при `install` → `stat -c %a var` возвращает 755 вместо 700, тест прав падает.

**Мутант:** сменить владельца одного файла на другой UID → `doctor` падает.

### 4.8 `run/` без overlay

Overlay — это `mount()`, то есть root. `run/` — только pid, lock-ссылка, сокеты, `instance.json`, `migration.json`, `migration-report.json`.

**Мутант:** добавить overlay-монтирование в `run/` → архитектурный тест падает.

## 5. Резолвинг

```
home:     --home       > NEMEQ_HOME     > $HOME/.nemeq
instance: --instance   > NEMEQ_INSTANCE > "default"
var:      --state-root > NEMEQ_VAR_ROOT > <home>/instances/<instance>/var
store:    --store      > NEMEQ_STORE    > <var>/store
```

1. Все переопределения абсолютны; относительный путь — код 2.
2. `--state-root`/`--store` вне `<home>` — только с `--allow-outside-home`.
3. При env-переопределении печатается `source=env(...)` в `nqctl status`.
4. `$HOME` пуст/отсутствует и нет `--home`/`NEMEQ_HOME` → код 2. Фоллбэк на CWD или `/` запрещён.
5. Каталоги создают только `install`/`migrate`; `apiserver` без `init` → `NemeqNotInitialized`.
6. Имя инстанса: `^[a-z0-9][a-z0-9_-]{0,31}$`; `..`, `/`, `\`, NUL — отказ до файловых операций.
7. Каноникализация: все пути через `os.path.realpath`; сравнение стора по realpath.

**Мутант:** передать относительный `NEMEQ_HOME=./x` → код 2.

**Мутант:** передать `--instance ../x` → код 2 до любой файловой операции.

**Мутант:** запустить с `env -u HOME` → код 2.

## 6. Инстансы

### 6.1 Идентичность: `home_id`, `store_id`, `instance_id`

| Поле | Где | Что идентифицирует | Меняется ли |
|---|---|---|---|
| `home_id` | `config/home.toml` | установку (префикс) | только новым install |
| `store_id` | метаданные стора **и** `instance.toml` | **данные стора** | **никогда** (переезжает с данными) |
| `instance_id` | `instance.toml` | конкретный инстанс в префиксе | при каждом `migrate --into-instance` |

`instance.toml` также содержит `lineage: {origin_home_id, origin_instance_id, migrated_at}`.

При старте сверяются три: `home_id` конфига против `home.toml`; `store_id` конфига против метаданных стора; `instance_id` против `run/instance.json`. Расхождение любого → код 5.

**Мутант:** подменить `store_id` в `instance.toml` → сервис не стартует с кодом 5.

**Мутант:** подменить `store_id` в одном инстансе → второй продолжает работать (проверка независимости).

### 6.2 Порты

Дефолт — фиксированный `8448`. Занят → код 3 с именем владельца (по `instances/*/run/instance.json`), **без автоинкремента**. Эфемерный `0` — явная опция.

`run/instance.json`: `{name, home_id, store_id, instance_id, pid, port, started_at, store_realpath, sandbox: {...}}`.

**Мутант:** запустить два инстанса с портом 8448 → второй падает с кодом 3, сообщение называет виновника, в стор не пишет.

### 6.3 Жизненный цикл

`nqctl instance create|list|status|destroy`. `create` — `0700`/`0600`; `destroy` требует остановленного сервиса, берёт лок стора, удаляет `var/ config/ logs/ run/`, `lib/` не трогает. Lock-файл `<var>.lock` **не удаляется** (§7.1).

**Мутант:** вызвать `destroy` при живом сервисе → код 4.

**Мутант:** удалить lock-файл в конце `destroy` → тест «конкурентный старт после destroy» падает (два владельца).

### 6.4 Lock живёт рядом со стором (закрывает B1)

В v0.3 лок лежал в `<store>/lock`, из-за чего: digest зависел от pid внутри лока, лок копировался при миграции, после `rename` flock оставался на отсоединённом inode, а `destroy` с удалением файла давал unlink-lockfile race.

**Нормативно:**

```
<var>.lock                       # рядом с var/, не внутри
open(O_RDWR|O_CREAT|O_NOFOLLOW, 0600)
flock(LOCK_EX|LOCK_NB)
```

- имя вычисляется от `realpath(store)`, а не от имени инстанса — привязка к стору сохраняется;
- lock-файл **никогда не удаляется** (`unlink` запрещён);
- lock **исключён** из `store_digest`, из копирования при миграции и из списка удаляемого в `destroy`;
- при удержании — сообщение `store busy: pid N`, код 4.

**Мутант:** перенести lock внутрь `var/store/` → тест «digest до/под/после лока совпадает» падает.

**Мутант:** добавить `unlink(lock)` в `destroy` → тест «destroy + конкурентный старт» падает (два владельца).

**Мутант:** запустить два инстанса с разными именами и одним `--store` → второй падает с кодом 4.

### 6.5 systemd — best-effort песочница

Дефолт — user-unit `~/.config/systemd/user/nemeq-<instance>.service`. Системные unit — уровень (в). Абсолютный путь прописывает `nqctl install-unit`; `%h` запрещён.

**Формулировка понижена до best-effort** (в v0.3 обещала больше, чем даёт user-unit): `ProtectSystem=strict` и `ReadOnlyPaths` применяются только при доступных unprivileged user namespaces; если их нет, systemd применяет unit **без** песочницы.

Шаблон:

```
Environment=NEMEQ_HOME=<abs>
Environment=NEMEQ_INSTANCE=<name>
ExecStart=<abs>/bin/nqctl serve
Restart=on-failure
KillMode=mixed
TimeoutStopSec=20
NoNewPrivileges=yes
PrivateTmp=yes
ProtectSystem=strict
ReadWritePaths=<abs>/instances/<name>/var
ReadWritePaths=<abs>/instances/<name>/logs
ReadWritePaths=<abs>/instances/<name>/run
ReadOnlyPaths=<abs>/lib
```

**Runtime-самопроверка:** `serve` на старте читает `/proc/self/status` (`NoNewPrivs`) и `/proc/self/mountinfo` (ro-монтирование `lib`) и записывает фактические значения в `run/instance.json → sandbox`. `doctor --hardened` требует их наличия; без них сервис помечает себя `sandbox: false` и продолжает.

`install-unit` берёт пути из `nqctl env --json`. Если фактический `store_realpath` не совпадает с юнитом — отказ при старте с текстом «regenerate unit».

**Lingering:** по умолчанию сервис живёт, пока активна сессия пользователя. Работа после logout и на загрузке требует `loginctl enable-linger <user>` — отдельное действие с привилегией.

**Мутант:** вставить `%h` в шаблон юнита → тест `grep -c '%h'` падает.

**Мутант:** расширить `ReadWritePaths` на весь префикс → тест «процесс не может писать в lib» падает.

**Мутант:** отключить `enable-linger` в фикстуре → тест «сервис поднимается после logout» падает.

## 7. Миграция

### 7.1 Предусловия и лок

- сервис **остановлен**; при живом — код 2 и «stop nemeq-<i> first». `--force` не существует;
- target непуст → код 2 (флага слияния нет, §7.6);
- locks источника и target удерживаются **всё** время миграции;
- lock-файлы `<var>.lock` **не копируются** и не удаляются.

**Мутант:** запустить `migrate` при живом сервисе → код 2 и в target не создано ни одного файла.

**Мутант:** скопировать `<var>.lock` в staging → `store_digest` staging расходится с источником, шаг проверки даёт код 10.

### 7.2 Crash-safe состояние (закрывает B2)

`run/migration.json` + `fsync` файла и каталога `run/` на каждом переходе.

| Состояние | Сделано | Повторный запуск |
|---|---|---|
| `prepared` | маркер записан и `fsync`, staging создан | удаляет staging, начинает заново (или `--continue`) |
| `copying` | идёт копирование | `--continue` дописывает по манифесту |
| `verifying` | копия готова, идёт fsck+digest | повторяет проверку |
| **`publishing`** | intent записан и `fsync` **до** `rename` | см. правило ниже |
| `published` | `rename` выполнен | дописывает отчёт |
| `reported` | отчёт записан | ничего, успех |
| `failed:<reason>` | ошибка | печатает причину, требует `--restart` |

**Правило восстановления `publishing`** (окно, которого не было в v0.3):

- `var` существует ∧ staging отсутствует ∧ манифест совпал → считать опубликованным, дописать отчёт, данные не трогать;
- `var` отсутствует ∧ staging существует → вернуться в `verifying`;
- оба существуют → код 11, ручное разбирательство, ничего не удалять.

**Манифест и его digest лежат в `run/`, не в staging** — иначе после `rename` посторонний файл окажется в корне `var/` и strict-`fsck` опубликованного стора упадёт.

**Порядок (нормативный):**

1. взять лок источника и target;
2. сравнить `st_dev(staging_parent)` с `st_dev(dirname(target_var))` — до создания `target_var`;
3. записать `prepared` + `fsync` файла + `fsync` каталога `run/`;
4. создать `var.migrating-<ts>/`;
5. копировать пофайлово (кроме `<var>.lock`); затем `fsync` всех файлов и каталогов staging;
6. `verifying`: `fsck` strict + сравнение `store_digest` источник↔staging;
7. `chown` по режиму §7.4; повторный `fsync`;
8. записать `publishing` + `fsync`;
9. `rename(staging → var)`; `fsync` родительского каталога;
10. `published`; записать отчёт в `run/migration-report.json` + `fsync`;
11. `reported`; отпустить локи.

**Мутант:** прервать процесс (`kill -9`) между шагами 9 и 10 → повторный запуск дописывает отчёт, `var` остаётся опубликованным и `fsck`-чистым.

**Мутант:** прервать между шагами 8 и 9 → повторный запуск возвращается в `verifying`, публикации не происходит.

### 7.3 `store_digest` — по содержимому, с каталогами (закрывает B3)

В v0.3 длина не была в байтах, каталоги были вне digest, а режимы не покрывались.

Каноническое кодирование. **Длина — всегда в байтах UTF-8**, сортировка — по байтам:

```
для каждого relpath (относительный, UTF-8, NFC) в порядке байтового возрастания:
    u64be(len_utf8(relpath)) || relpath || u8(kind)
    kind=0 (file):    u64be(size) || sha256(content) || u32be(mode & 0o7777)
    kind=1 (symlink): u64be(len_utf8(target)) || target
    kind=2 (dir):     (тело отсутствует)

store_digest = "sha256:" + sha256(D)
```

- обходятся все файлы и **все каталоги** под `<store>` (`store/`, `epishu/`, `state/`, `data/`, `anchor*`, включая `wal/`, `view/`, `paqidutu/`, `zikru-*`, `observability_log/`);
- `<var>.lock` **исключён по имени** (§6.4);
- NFC применяется, но имена, у которых NFC ≠ NFD, отвергаются при `install` (код 2) — иначе digest не различает две раскладки;
- sampling **запрещён**. Ускорение — только Merkle с сохранением полноты, отдельным решением.

**Мутант:** удалить пустой каталог `epishu/<id>/wal/` из staging → digest расходится, шаг 6 даёт код 10.

**Мутант:** подменить один байт в файле каждого класса (`atoms`, `view`, `paqidutu`, `wal`, `anchor`, `state`, `data`) → digest меняется в каждом случае.

**Мутант:** сменить режим файла `0644 → 0777` → digest меняется.

**Мутант:** переставить порядок обхода → digest не меняется (тест на стабильность).

### 7.4 Режимы миграции (закрывает B4)

В v0.3 `chown` требовал root, что противоречило allow-list, а rootless был невыполним для типового root-стора.

| Режим | Когда | Требования | Действие |
|---|---|---|---|
| **rootless** | источник целиком принадлежит целевому uid | запуск от целевого пользователя | `chown` не нужен |
| **root-assisted** | источник принадлежит root | root + явный `--root-assisted --target-uid N --target-gid N` | `os.lchown`/`os.chown` (без exec), затем нормализация режимов |
| **adopt-uid** | источник принадлежит сервисному uid (третьему) с явного разрешения | root + `--adopt-uid N` | владелец переносится на целевой uid, запись в отчёт |

- запуск от root **без** явного флага → код 2 (привилегия не применяется молча);
- `--target-uid 0` запрещён;
- проверка `--target-uid == st_uid($NEMEQ_HOME/config/home.toml)` — иначе код 2;
- `chown` распространяется и на `run/migration*.json`;
- файлы третьих uid без `--adopt-uid` → код 14 с перечнем.

**Мутант:** запустить миграцию root-стора без `--root-assisted` → код 2.

**Мутант:** запустить root-assisted с `--target-uid 0` → код 2.

**Мутант:** оставить `run/migration.json` с владельцем root после root-assisted → тест «все файлы HOME принадлежат целевому uid» падает.

**Мутант:** задать `--target-uid`, отличный от владельца `home.toml` → код 2.

### 7.5 Symlink

Копировать как ссылки, без dereference. Абсолютная ссылка с target вне источника — в отчёт и отказ (`--rewrite-links` переписывает префикс). Симлинк наружу источника — всегда отказ.

**Мутант:** создать `var/x -> /var/nemeq/var/y` в фикстуре → `migrate` отказывает, путь есть в отчёте.

**Мутант:** заменить относительную ссылку внутри стора на её dereference-копию → тест «`readlink` идентичен» падает.

### 7.6 Слияния нет (закрывает B8)

Флаг `--merge` **удалён**. Непустой target — всегда код 2. Слияние двух сторов не поддерживается и не будет: это требует отдельной спецификации разрешения конфликтов.

**Мутант:** передать удалённый флаг `--merge` → код 2 «unknown flag».

### 7.7 Источник не удаляется никогда

Флаг `--purge-source` удалён в v0.3. Вместо него `nqctl migrate --print-cleanup-cmd` **печатает** команду удаления и ничего не выполняет. Никакой сценарий `migrate` не удаляет источник.

**Мутант:** выполнить `migrate` до успеха → источник остаётся на месте; в stdout есть готовая команда.

**Мутант:** уронить `--verify-target` после публикации → источник всё равно на месте.

### 7.8 Anchor и WAL

Копируется явно: `store/`, `var/epishu/`, `var/state/`, `var/data/`, `anchor*`. `fsck` источника — strict. Непустой хвост WAL → код 6; `--recover` реплеит WAL в staging, digest сравнивается **после** реплея.

**Мутант:** оставить оборванную транзакцию в источнике → `migrate` отказывает с кодом 6 и перечнем.

**Мутант:** прогнать с `--recover` → digest совпадает, отчёт фиксирует число реплеенных записей, mtime/размер источника не изменились.

### 7.9 Коды возврата (закрывает B9)

Двусмысленность v0.3 (код 6 = и WAL, и version skew) устранена: version skew вынесен в 13.

| Код | Класс |
|---|---|
| 0 | успех |
| 2 | неверный вызов или предусловие (сервис запущен, target непуст, относительный путь, root без флага, неверное имя, NFC≠NFD, `--target-uid` ≠ владелец) |
| 3 | порт занят |
| 4 | лок занят |
| 5 | несовпадение идентичности или схемы (`home_id`, `store_id`, `instance_id`, `schema_version`) |

### 7.10 Переход уже развёрнутых alpha/beta (закрывает B5)

В v0.3 `instance_id` не мог одновременно идентифицировать стор и быть уникальным.

```
nqctl migrate --from-home /root/.nemeq --into-instance alpha --use-lib-from /srv/nemeq-lib
```

1. прочитать `home.toml` и `instance.toml` источника: `layout_version`, `nemeq_version`, `schema_version`, `store_id`;
2. `--use-lib-from` **обязателен** и **не может указывать на источник** (код 2) — иначе версия берётся из мигрируемого HOME, что и было противоречием v0.3;
3. сравнить `schema_version` источника с поддерживаемой выбранным `lib/` → выше: код 5;
4. сравнить `nemeq_version`: расхождение → код 13, флага обхода нет;
5. скопировать только `var/` в целевой инстанс;
6. `store_id` сохраняется (это те же данные); `instance_id` генерируется новый; `lineage` заполняется;
7. коллизия `store_id` с уже существующим инстансом → код 5 с указанием обоих путей и сравнением digest (копия или дивергенция);
8. каждый HOME мигрируется отдельно; слияние двух HOME в один инстанс — код 2.

**Мутант:** указать `--use-lib-from` равным `--from-home` → код 2.

**Мутант:** мигрировать две фикстуры-копии одного стора → вторая даёт код 5 и называет первый инстанс.

**Мутант:** мигрировать две фикстуры с разными `store_id` → обе проходят, `instance_id` уникальны, `store_id` сохранены.

## 9. Критерии приёмки

### 9.1 Ни одного пути ОС в любом файле

В v0.3 проверялись только `*.py`, `*.rs`, `*.sh`, `*.toml`, `*.service` — это deny-list, который всегда неполон.

Инвертированный тест: сканируются **все** файлы репозитория, allow-list исключений явный.

```sh
rg -a --hidden -g '!.git' -n -e '/(var|var/lib|opt|usr/local|etc|run)/nemeq|\.nq\b' \
  --glob '!massaru/legacy.py' --glob '!docs/**' --glob '!tests/fixtures/**'
```

плюс тест: каждый legacy-путь из §4.1 имеет строку в таблице §4.1.

**Мутант:** добавить `/var/nemeq` в шаблон `.j2`, в `bin/`-скрипт без расширения и в `.yml` → тест падает в каждом случае.

**Мутант:** удалить строку `/var/lib/nemeq` из таблицы §4.1 → тест соответствия падает.

### 9.2 Изоляция инстансов

Один id в двух инстансах с разным содержимым, оба читаются независимо; `realpath` сторов не пересекаются, inode разные; второй старт на том же сторе → код 4.

**Мутант:** подменить `NEMEQ_HOME` второго инстанса на первый → тест падает на сравнении inode.

### 9.3 Health как инвариант, а не доступность

`{instance, home_id, store_id, instance_id, rev, last_hash, fsck: clean, sandbox}`. До и после `restart`: `rev` не убывает, `last_hash` совпадает, идентификаторы те же.

**Мутант:** подменить `instance_id` в `instance.toml` при живом сторе → health отдаёт non-200 с кодом 5 (а не просто «сервис лежит»).

**Мутант:** вернуть в health `rev` на единицу меньший → тест сравнения до/после падает.

### 9.4 Целостность через `store_digest`

Сравнение по §7.3.

**Мутант:** подменить байт в `atoms` → digest расходится, миграция даёт код 10.

### 9.5 Чистота вне HOME

Полный набор файловых syscall'ов (`openat`, `open`, `creat`, `mkdirat`, `mkdir`, `rename`, `renameat`, `linkat`, `symlinkat`, `unlinkat`), затем снимок дерева до/после и сравнение **фактических изменений** вне HOME.

**Мутант:** записать в **существующий** файл вне HOME → тест чистоты падает (в v0.3 фильтр по `O_CREAT` это пропускал).

### 9.6 Установка без сети и без pip

1. `unshare -n` — install и старт проходят;
2. с сетью + `strace -e connect,sendto` — ноль попыток наружу;
3. `pip`/`ensurepip` отсутствуют в `PATH` (проверяется в тесте);
4. smoke-импорт каждого пакета из `deps.lock`.

**Мутант:** добавить вызов `urllib.request` в `install` → тест (2) падает на `connect`.

1. install и старт от непривилегированного пользователя;
2. повторный `install` сохраняет `rev`/`last_hash`, не плодит инстансы;
3. `uninstall --purge` не оставляет процессов, локов, unit'ов;

**Мутант:** смонтировать NFS в фикстуре → тест (6) падает.

### 9.9 Симлинк `var` не авторитетен

`$NEMEQ_HOME/var -> instances/default/var` создаётся только при install. Путями не служит: вычисления только через резолверы. `doctor` проверяет цель.

**Мутант:** перенаправить симлинк на `instances/alpha/var` → `doctor` падает до любой записи.

### 9.10 Инструменты критериев проверены

`crit_lint.py --selftest` и `metamutant.py --selftest` обязаны проходить в CI. При отсутствии `pytest` метамутант выдаёт SKIP (не PASS) и приёмочный тест это видит.

**Мутант:** сломать `crit_lint` так, чтобы он не находил отсутствующий мутант → его собственная фикстура падает.

**Мутант:** убрать из `metamutant` различение инфраструктурного падения → selftest падает на вакуумном мутанте.
