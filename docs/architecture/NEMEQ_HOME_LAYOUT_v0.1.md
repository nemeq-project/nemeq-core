# NEMEQ_HOME_LAYOUT v0.1 — пути внутри домашнего каталога и самодостаточная поставка

**Дата:** 2026-11-26 · **Статус:** предложение к обсуждению · **Автор:** Верста
**Затрагивает:** SDD v0.5 §4, TEXTSTORE v0.3.x, ARCH_SERVICES v0.1, `massaru/layout.py`, `nqctl`, `apiserver`, `massaru/cli.py`

---

## 0. Два принципа, из которых следует всё остальное

### 0.1 Self-contained поставка

**Nemeq не должен требовать внешних зависимостей на машине установки.** Всё, что нужно для
работы, приезжает вместе с дистрибутивом:

- нет `pip install` из сети — зависимости кладутся в дистрибутив;
- нет `ensurepip` и системного `python3-venv` — рантайм приезжает с собой;
- нет обращений к `pypi.org`, зеркалам и любым реестрам во время установки и запуска;
- установка на машине без сети — штатный режим, а не аварийный обход.

Основание — фактическое состояние целевых машин. На `c-nemeq` (amgm, Ubuntu 24.04)
**отсутствуют** `pip` и `ensurepip`, а `pypi.org` и `mirrors.aliyun.com` отвечают таймаутом.
Единственный работающий путь установки там — офлайн-распаковка колёс.

### 0.2 Целевая платформа — Rust

Конечная цель — переписать nemeq-core на Rust. Как только это произойдёт, требование
§0.1 становится тривиально выполнимым: один статически слинкованный бинарь (или набор
бинарей) на нужную архитектуру, без интерпретатора, без site-packages, без venv.

До переписывания действует переходное правило: **Python-поставка обязана вести себя так,
как будто Rust-бинарь уже есть** — то есть быть переносимой и не зависеть от окружения
хоста. Всё, что нарушает это правило, считается техническим долгом с явным сроком.

**Следствия для текущего Python-этапа:**

1. Зависимости поставляются как артефакты (wheel-архив или распакованный `lib/`), а не
   ставятся из сети.
2. Никаких обращений к системным путям `/opt`, `/var`, `/run` ОС — только внутрь
   `$NEMEQ_HOME` (§1).
3. Код не должен импортировать пакеты, которых нет в поставляемом наборе.
4. Проверка приёмки — установка на машине без сети и без `pip` (§8).

## 1. Проблема: пути ОС, общие на всю машину

Сейчас nemeq использует абсолютные пути:

| Путь | Назначение | Где зашит |
|---|---|---|
| `/var/nemeq` | корень состояния, `epishu/`, `state/`, `data/` | `massaru/layout.py:13` |
| `/var/nemeq/apiserver` | стор аписервера | `nqctl/cli.py:21`, `massaru/store_fsck.py:38`, `apiserver/__main__.py:32` |
| `/opt/nemeq/{zi,su}` | неизменяемые образы | SDD v0.5 §4 |
| `/run/nemeq` | runtime, overlay, pid | SDD v0.4 §4, TESTS T-01 |

Следствия:

1. Два инстанса на одной машине **конфликтуют**: общий `/var/nemeq`, один `flock`, один стор.
2. Установка требует root и пишет в системные каталоги — нельзя поставить «для пользователя».
3. Удаление инстанса = ручная зачистка четырёх разнесённых каталогов.
4. Нет переносимости: скопировать инстанс на другую машину невозможно.

Проверено на `c-nemeq` (amgm): до переделки там были пустые `/opt/nemeq`, `/var/nemeq`,
`/var/lib/nemeq`, `/run/nemeq` — **0 файлов, ни одной установки** nemeq.

## 2. Как делают аналоги

### 2.1 Hermes — `~/.hermes`

Корень состояния — `/home/hermes/.hermes` (27 подкаталогов: `config.yaml`, `auth.json`,
`cache/`, `cron/`, `logs/`, `environments/`, `hermes-agent/` — сам код).

Разделение инстансов — **переменной окружения на процесс**:

```
/etc/hermes-runtime-bridge/bridge.env:8   HERMES_HOME_ROOT=/var/lib/hermes-runtime-bridge/homes
server.py:492                             path = Path(HERMES_HOME_ROOT) / session_id
server.py:535                             env["HERMES_HOME"] = str(hermes_home(session_id))
```

Корень задаётся переменной, а не константой в коде; на каждый инстанс — свой `HERMES_HOME`.

### 2.2 OpenCode — XDG

Раскладка по XDG Base Directory:

| Что | Где |
|---|---|
| конфиг | `~/.config/opencode/` (`opencode.json`, `AGENTS.md`) |
| данные | `~/.local/share/opencode/` (`opencode.db`, `repos/`, `log/`) |
| кэш/состояние | `XDG_CACHE_HOME`, `XDG_STATE_HOME` |
| бинарь | `~/.opencode/bin/opencode` |

Переопределение — `OPENCODE_CONFIG_DIR`, `OPENCODE_CONFIG`, `OPENCODE_DB`. Второй инстанс
сделан обёрткой `opencode2` над тем же бинарём с другим окружением.

**Вывод:** оба держат всё в домашнем каталоге, инстанс различают переменной окружения
(Hermes) либо XDG-каталогом (OpenCode). Ни один не пишет в `/opt` и `/var` ОС.

## 3. Предлагаемая раскладка

```
$NEMEQ_HOME/                      # по умолчанию ~/.nemeq
├── bin/                          # точки входа
│   ├── nqctl
│   ├── nemeq-apiserver
│   ├── nemeq-massaru
│   └── nemeq-env                 # экспорт переменных инстанса
├── config/
│   ├── instance.toml             # имя, порт, лимиты
│   └── nq.json                   # url/actor для nqctl (вместо ~/.nq/config)
├── lib/                          # immutable: код и зависимости
│   ├── nemeq-core/
│   └── pydeps/
├── state/                        # mutable
│   ├── store/
│   ├── epishu/<id>/
│   ├── state/
│   └── data/
├── logs/
└── run/                          # pid, сокеты, overlay
```

Соответствие старым путям:

| Было | Стало |
|---|---|
| `/var/nemeq` | `$NEMEQ_HOME/state` |
| `/var/nemeq/apiserver` | `$NEMEQ_HOME/state/store` |
| `/opt/nemeq` | `$NEMEQ_HOME/lib` |
| `/run/nemeq` | `$NEMEQ_HOME/run` |

Внутри инстанса структура `epishu/<id>/{wal,atoms,traces,...}` **не меняется** — контракт
SDD v0.4 §4 (02b) и TEXTSTORE сохраняется, меняется только корень.

## 4. Правила резолвинга

Единая функция `resolve_home()` для всех точек входа, порядок приоритета:

1. `--home` (явный аргумент CLI)
2. `NEMEQ_HOME` (переменная окружения)
3. `~/.nemeq` (по умолчанию)

Никаких обращений к `/var`, `/opt`, `/run` ОС в коде. Каталог создаётся при `install`,
а не при чтении.

Обратная совместимость: `NEMEQ_VAR_ROOT` и `NEMEQ_STORE` остаются явными переопределениями
для тестов, но **перестают быть значениями по умолчанию**. Это ломающее изменение для
существующих установок — нужен `nqctl migrate` (§6).

## 5. Несколько инстансов

Три уровня, по возрастанию изоляции:

**а) Профиль в одном HOME** — как Hermes:

```sh
nqctl --home ~/.nemeq/profiles/alpha ...
nqctl --home ~/.nemeq/profiles/beta ...
```

Один пользователь, разные данные, общий код в `lib/` (экономия ~30 МБ на инстанс).

**б) Отдельный HOME** — как два пользователя (проверено на `c-nemeq`):

```
/root/.nemeq      → порт 8448, сервис nemeq-alpha
/home/beta/.nemeq → порт 8449, сервис nemeq-beta
```

**в) Полная изоляция** — отдельный UID/mount-ns на инстанс (это SDD v0.4 §5 для Awilu,
не для установки).

Рекомендация: поддержать **(а)** и **(б)**, (в) оставить в SDD для Awilu.
Имя unit-файла обязано включать имя инстанса (`nemeq-<instance>.service`) — иначе два
инстанса не уживутся в systemd.

## 6. Миграция

`nqctl migrate --from /var/nemeq --home ~/.nemeq`:

1. проверяет, что источник не занят писателем (`flock`);
2. копирует `epishu/`, `state/`, `data/` с сохранением прав;
3. сверяет `rev` и `last_hash` через `fsck` **до и после**;
4. только при совпадении удаляет старый каталог (или оставляет по `--keep`).

Без сверки `fsck` миграция не считается успешной.

## 8. Критерии приёмки

1. `grep -rn "/var/nemeq\|/opt/nemeq\|/run/nemeq" --include=*.py` → пусто.
2. Два инстанса в одном контейнере работают одновременно, данные изолированы:
   объект из alpha в beta → `404`.
3. `systemctl restart` обоих → `health ok`.
4. `nqctl migrate` с `fsck`-сверкой: `rev` и `last_hash` совпадают.
5. После установки вне `$NEMEQ_HOME` не создаётся **ни одного** каталога.
6. Установка на машине **без сети и без `pip`/`ensurepip`** проходит и даёт рабочий
   инстанс (проверка принципа §0.1).
7. Тесты: резолвинг (`--home` > `NEMEQ_HOME` > `~/.nemeq`) и изоляция двух HOME.

## 9. Проверено на практике (c-nemeq, 2026-11-26)

Временная раскладка (скриптами, без правок в коде) развёрнута и работает:

- `alpha`: `/root/.nemeq`, порт 8448, `nemeq-alpha.service` — active + enabled
- `beta`: `/home/beta/.nemeq`, порт 8449, `nemeq-beta.service` — active + enabled
- по 30 МБ каждый; каталоги ОС удалены, сервисы остались живы
- изоляция: запись в alpha → в beta `404 NotFound`
- `intruder` → `403` на обоих
- повтор после `systemctl restart` → `health ok` на обоих
- установка выполнена **офлайн**: `pip`/`ensurepip` отсутствуют, сеть недоступна,
  зависимости распакованы из 11 wheel-архивов (`cp312`) в `lib/pydeps`

Это доказывает жизнеспособность схемы и принципа §0.1. Осталось перенести в код по §7.

## 10. Открытые вопросы

1. **Профили vs отдельные HOME** — дефолт: профиль в одном HOME (экономия `lib/`) или
   отдельный пользователь (жёстче изоляция)?
2. **`/proc/nemeq` и TESTS T-01** — тест требует bind-mount `ro` и `EACCES`. Внутри
   `$NEMEQ_HOME` это уже не `/proc`; переформулировать на `$NEMEQ_HOME/run` или оставить
   `/proc` только для случая полной изоляции (§5в)?
3. **Формат поставки зависимостей** до Rust-этапа — wheel-архив рядом с дистрибутивом
   или уже распакованный `lib/pydeps` в поставке?
