## Блокеры (совпали у обоих)

### B1. Лок внутри стора ломает digest, миграцию и destroy

**Оба отметили первым пунктом.** Sonnet разобрал подробнее, у него пять следствий:

1. **digest невоспроизводим.** §7.3 хеширует все файлы под `<store>`, а §6.4 кладёт туда `lock` с pid внутри. digest без лока ≠ digest с локом.
2. **миграция ломается сама о себя.** §7.1 держит лок источника всё время, §7.2 шаг 6 сравнивает digest источник↔staging — с разными lock-файлами. Результат: код 10 при **корректной** копии.
3. **лок копируется в staging** вместе с `store/`.
4. **лок теряется после `rename`.** Шаг 8 подменяет каталог, flock остаётся на отсоединённом inode, новый `var/store/lock` — другой inode. Третий процесс получает лок, хотя первый ещё жив.
5. **race при destroy.** §6.3 берёт лок и удаляет `var/`; повторный `open(O_CREAT)` создаёт новый inode → два «владельца» одновременно (классический unlink-lockfile race).

**Решение:** лок вне копируемого/переименовываемого/удаляемого поддерева. Имя вычисляется от `realpath(store)`, но файл лежит рядом со стором, не в нём: `<var>.lock`. Lock-файл **никогда не удаляется** (`unlink` запрещён). Если оставлять в сторе — то исключить из digest по имени, из копирования и из destroy; все три пункта нормативно.

**Мутанты:** digest до/под/после лока совпадает; `migrate` при удержанном локе источника даёт 0, не 10; после `rename` третий процесс лок не получает; `destroy` + конкурентный старт → ровно один жив.

### B2. Окно `rename` → `published` без состояния

Sonnet: при `kill -9` между шагами 8 и 9 в `migration.json` остаётся `verifying`, но staging уже переименован, а `var/` непуст → предусловие «target непуст → код 2». Миграция состоялась, но система отказывается и продолжать, и откатывать. Отчёт (`reported`) не запишется никогда. **Заявление «kill -9 на любом шаге восстанавливается» ложно.**

Гермес подтверждает тем же пунктом.

Дополнительно (Sonnet): манифест копирования пишется **внутрь** `var.migrating-<ts>/` и после rename оказывается в `var/` → посторонний файл в корне стора, strict-`fsck` падает, digest опубликованного `var` ≠ digest источника.

И: шаг 2 сравнивает `st_dev(target_var)` до создания `target_var` (шаг 4) → `ENOENT`.

**Решение:** состояние `publishing`, записывается и `fsync` **до** `rename` (intent log). Манифест и его digest — в `run/`, не в staging. Правило восстановления: `var` есть ∧ staging нет ∧ манифест совпал → считать опубликованным, дописать отчёт, данные не трогать. `st_dev` сравнивать с `st_dev(dirname(target_var))`.

### B3. `store_digest` — снова вакуумный критерий

Sonnet нашёл ровно то, чего я боялся больше всего — **третий раз подряд**:

- `u64be(len(relpath))` не задаёт, что длина в **байтах UTF-8**. При `len(str)` (кодпоинты) на не-ASCII путях рамка разбора рвётся → **две разные структуры стора могут дать одинаковый digest**.
- **Пустые каталоги вне digest.** Компенсация через `dirs[]` **в отчёте** — значит digest не является идентичностью стора: потеря `epishu/<id>/wal/` digest не меняет, шаг 6 её не видит.
- Мой мутант «добавить пустой каталог → меняется `dirs[]`» — **мутант на отчёт, а не на критерий §8.4**. Ровно тот же класс ошибки, что §8.1 в v0.1 и §6.3 в v0.2.
- Нет режимов прав и владельца в `D`, хотя §4.7 считает их инвариантом.

**Решение:** `len = len(utf8(...))` явно; каталоги включить в `D` записью `kind=2`; в запись файла добавить `u32be(mode)`; сортировка по байтам UTF-8; NFC убрать или явно отвергать имена с NFC≠NFD.

**Мутанты:** удалить пустой каталог из staging → digest расходится, шаг 6 даёт 10. `chmod 0644→0777` → digest расходится. Путь в NFD и NFC → разный digest или отказ.

### B4. Миграция root→user невыполнима для типового случая

Sonnet: типовой legacy-инстанс — `/var/nemeq` с владельцем root **или сервисным uid**. Сервисный uid → «файл третьего uid» → отказ в обоих режимах. root-owned → rootless неприменим. То есть **штатный путь — всегда root-assisted**, и «работа без root» из §8.8 к миграции не относится.

При root-assisted (Sonnet):
- `chown -R` **не входит в allow-list §2.3** — прямое противоречие;
- `chown` не сбрасывает режимы → копирование под root расширит права против §4.7;
- `run/migration.json` пишет root и не chown'ит → сервис не может перезаписать, а §8.8.8 падает на своей же приёмке;
- нет проверки `--target-uid` против владельца `home.toml` — root может отдать стор чужому uid;
- нет кода отказа для «файлы чужого uid», хотя таблица §7.9 заявлена полной.

**Решение:** третий режим `--adopt-uid N` (перенос владельца из источника в целевой uid с записью в отчёт); `chown` через `os.chown`/`os.lchown` **без exec** и внести в §2.3; после копирования нормализация режимов по §4.7 и chown **всего**, включая `run/`; проверка `--target-uid == st_uid(home.toml)`; новый код в §7.9.

### B5. `instance_id` не может быть и идентификатором стора, и уникальным для инстанса

Sonnet: если генерируется при установке — две копии одного стора получают разные id, и «`instance_id` идентифицирует стор» ложно. Если копируется с данными — шаг 5 даёт коллизию и код 5, то есть сценарий §7.10 не проходит для второго HOME.

Плюс: копирование `var/` копирует метаданные с тем же `instance_id`, поэтому сверка «конфиг против метаданных» после миграции **тождественно проходит** и коллизию обнаружить не может.

И противоречие в шаге 4: «`lib/` берётся из `--use-lib-from`, а не из источника», а в примере `--use-lib-from /root/.nemeq` — то есть **из источника**.

**Решение:** развести `store_id` (в метаданных стора, переезжает с данными, неизменяем) и `instance_id` (новый при каждом `migrate --into-instance`), плюс `lineage: {origin_home_id, origin_instance_id, migrated_at}`. Коллизию ловить по `store_id`. `--use-lib-from` обязателен и не равен источнику, либо убрать.

## Блокеры, найденные одним из ревьюеров

### B6. `/var/lib/nemeq` пропущен и в §8.1, и в §4.1 (Sonnet)
§3 перечисляет `/var/lib/nemeq` как один из четырёх legacy-каталогов, но:
- паттерн §8.1 `/(var|opt|run)/nemeq` его **не матчит** (`/var/lib/nemeq`);
- правил миграции для него нет в §4.1 — только для элементов **внутри** `/var/nemeq/`.

Существующая установка с `/var/lib/nemeq` **не мигрируется и не отвергается — просто игнорируется**, данные остаются.

Плюс охват §8.1 неполон: нет файлов без расширения (`bin/*` шимы), `*.json`, `*.j2`/`*.tmpl` (шаблоны юнитов), `*.yml`, `Makefile`, `Dockerfile`, `*.socket`/`*.timer`/`*.conf`. `git grep` не смотрит сгенерированный `lib/`.

**Решение:** инвертировать тест — сканировать **все** файлы (`rg -a --hidden -g '!.git'`) с allow-list исключений, а не deny-list расширений. Паттерн расширить до `/(var|var/lib|opt|usr/local|etc|run)/nemeq` + `\.nq\b`. Отдельный тест: каждый legacy-путь из §3 имеет строку в §4.1.

### B7. Правило мутантов нарушено собственной спецификацией (оба)
- **§8.3:** критерий — инварианты `rev`/`last_hash`/`identity` через restart, а мутант — «остановить стор → health non-200». Это проверка **доступности**, не инварианта: сломайте сверку `instance_id` или сбросьте `rev` — тест останется зелёным.
- **§8.7 и §8.8** вообще без мутантов, хотя §0 объявляет критерий без мутанта недействительным.
- **§4.3** (Гермес): мутант не гарантирует падение.

**Решение:** §8.3 — мутант «подменить `instance_id` при живом сторе → non-200 с кодом 5» и «подменить `rev` на меньший → падение». §8.7/§8.8 — по мутанту на пункт. Формальный линтер по `docs/architecture/*.md`: у каждого `§8.x` есть непустая строка «Мутант:». Отдельный **метамутант**: прогнать каждый мутант и убедиться, что соответствующий тест краснеет.

### B8. `--merge` без контракта (Гермес)
§7.1 упоминает `--merge`, но не определяет семантику: что сливается, что при конфликте ключей, как считается digest.

**Решение:** либо убрать флаг, либо описать: слияние по ключам, конфликт → код 5 с перечнем, digest считается после слияния и сравнивается с ожидаемым объединением.

### B9. Код 6 двусмыслен (Гермес)
В §7.9 код 6 = «грязный WAL», в §7.10 — «version skew». Два несовместимых значения.

**Решение:** version skew → отдельный код 13, либо всегда отказ (см. ниже).

### B10. Sandbox в user-unit не гарантирован (оба)
Sonnet: `ProtectSystem=strict`/`ReadOnlyPaths` в user-юните применяются только при доступных unprivileged user namespaces. Если их нет, systemd **не отказывается**, а применяет unit **без** песочницы. То есть «запись в `lib/` из-под unit → отказ» — не гарантия, а зависящее от хоста поведение.

Плюс: юнит генерируется с абсолютными `ReadWritePaths`, а §5 разрешает `--store` вне `<home>` — тогда сервис либо не может писать, либо оператор руками расширяет `ReadWritePaths`, и сужение испаряется.

**Решение:** понизить формулировку до **best-effort**; `serve` на старте пишет в `run/instance.json` фактические флаги (`NoNewPrivs`, ro-монтирование `lib` из `/proc/self/status`/`mountinfo`); `doctor` требует их для «hardened»-профиля. `install-unit` берёт пути из `nqctl env --json`, при расхождении фактического `store_realpath` — отказ при старте с текстом «regenerate unit».

## Итог

**Третий раз подряд я сдала вакуумный критерий.** Это не случайность, а системная ошибка процесса:

| Итерация | Вакуумный критерий | Почему |
|---|---|---|
| v0.1 | §8.1 `grep` | `\|` без `-E` ищет литерал |
| v0.2 | §6.3 `store_digest` | формула без хешей содержимого |
| v0.3 | §7.3 `store_digest` | `len()` не в байтах; каталоги вне digest; мутант на отчёт, не на критерий |

**Что менять в процессе, а не в документе:**

1. **Метамутант как обязательный шаг.** Не «описать мутант», а **прогнать** его: сломать код и убедиться, что тест краснеет. Описанный мутант без прогона — это намерение, а не проверка.
2. **Формальный линтер по документу.** Каждый критерий `§8.x` обязан иметь непустую строку «Мутант:». Линтер запускается до отправки на ревью, а не после.
3. **Правило «одна формула — один мутант на каждый вход».** Для digest: мутант на каждый класс файлов, на каждый тип записи, на кодирование длины.

**Реализацию не начинать** до закрытия B1–B10.

**Что подтверждено:** принципы §2 (self-contained, разделение зависимостей), раскладка §4 в целом, резолвинг §5, схема §7.9 в основе. Проблемы — в деталях миграции, целостности и идентичности, то есть в самой сложной части.
