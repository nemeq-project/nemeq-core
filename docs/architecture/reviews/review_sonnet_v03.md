## Замечания

### 1. §6.4 + §7.3 → lock внутри стора делает `store_digest` невоспроизводимым, а локи — невалидными
`§6.4` кладёт lock в `<store>/lock`, `§7.3` хеширует **все** файлы под `<store>`. Значит digest зависит от наличия/содержимого эфемерного lock-файла, который создаётся при каждом открытии и (по тексту `StoreBusy: pid N`) содержит pid. Следствия: (а) digest, снятый без лока, ≠ digest, снятый с локом; (б) `§7.6` «копируется явно: `store/`» копирует lock в staging; (в) `§7.1` держит локи **всё** время миграции, то есть сравнение источник↔staging в шаге 6 идёт по разным lock-файлам → код 10 при полностью корректной копии; (г) `§7.2` шаг 8 `rename(staging → var)` подменяет каталог, внутри которого лежит залоченный inode: удержанный flock оказывается на detached inode, а новый `var/store/lock` — другой inode, лок тихо потерян, третий процесс стартует; (д) `§6.3` `destroy` берёт лок и удаляет `var/` → повторный `open(O_CREAT)` создаёт **новый** inode, два «владельца» лока одновременно (классический unlink-lockfile race).
**Предложение:** лок вынести за пределы того поддерева, которое копируется/переименовывается/удаляется: `<home>/instances/<name>/lock` **или** `<var>.lock` рядом со стором, имя вычислять от `realpath(store)` (это сохраняет привязку к стору из B5 и не привязывает к имени инстанса). Никогда не `unlink` lock-файл. Если оставлять lock в сторе — он обязан быть исключён из `D` по имени, исключён из копирования и не удаляться при destroy; все три пункта записать нормативно.
**Как проверить:** тест «digest(store) до взятия лока == digest(store) под локом == digest(store) после»; тест `migrate` при удержанном локе источника (ожидается 0, не 10); тест «destroy + конкурентный старт» — ровно один жив; тест «после rename третий процесс не получает лок».

### 2. §7.2 → окно `rename`→`published` не имеет состояния: повторный запуск не может ни продолжить, ни откатить
Нормативный порядок: шаг 8 `rename`, шаг 9 `published`. При `kill -9` между ними в `migration.json` остаётся `verifying`. Повторный запуск в состоянии `verifying` «повторяет проверку» staging — которого уже нет (он переименован), а `var/` уже непуст → срабатывает предусловие `§7.1` «target непуст → код 2». Итог: миграция состоялась, но система считает её невалидной и отказывается и продолжать, и откатывать; отчёт (`reported`) не будет записан никогда. Заявление «`kill -9` на любом шаге оставляет состояние, из которого повторный запуск либо завершает, либо откатывает» ложно. Дополнительно: манифест копирования пишется **внутрь** `var.migrating-<ts>/` (шаг 4) и после rename оказывается в `var/` → посторонний файл в корне стора, ломает strict-`fsck` опубликованного стора и делает digest опубликованного `var` отличным от digest источника, который сравнивался в шаге 6; шаг 9 «дописывает отчёт из манифеста staging-метаданных» обращается к файлу, лежащему уже внутри опубликованного стора. Ещё: шаг 2 делает `st_dev(target_var)` до того, как `target_var` создан (шаг 4) → `ENOENT`.
**Предложение:** ввести состояние `publishing`, записываемое и `fsync` **до** `rename` (intent log), плюс манифест и его digest в `run/`, не в staging. Правило восстановления: `var` существует ∧ staging отсутствует ∧ манифест совпал → считать опубликованным, дописать отчёт, не трогать данные. `st_dev` сравнивать с `st_dev(dirname(target_var))`.
**Как проверить:** fault injection ровно в точке «после rename, до записи маркера» и «после маркера, до отчёта»; после `--continue` — отчёт существует, `fsck` published-стора чист, в корне `var/` нет файлов манифеста.

### 3. §7.3 → `len(relpath)` не задан как длина в байтах; пустые каталоги вне digest (критерий снова вакуумный)
Формула `u64be(len(relpath)) || relpath` не говорит, что длина — это длина **UTF-8-байтов**. При реализации через `len(str)` (кодпоинты) на не-ASCII путях префикс длины не совпадает с фактическим числом байтов → рамка разбора рвётся, и две разные структуры стора могут дать одинаковый `D`. То же для `len(target)`. Второе: каталоги исключены, компенсация — `dirs[]` **в отчёте**, то есть `store_digest` не является идентичностью стора: потеря при миграции пустого каталога (`epishu/<id>/wal/`, `view/`) digest не меняет, проверка шага 6 её не видит. Мутант «добавить пустой каталог → меняется `dirs[]`» — это мутант на отчёт, а не на критерий `§8.4`; это ровно тот же класс ошибки, что v0.1/v0.2. Третье: в `D` нет режимов прав и владельца, хотя `§4.7` считает их частью инварианта.
**Предложение:** зафиксировать `len = len(utf8(relpath))` и `len = len(utf8(target))` явно; включить каталоги в `D` записью `kind=2 || u64be(len(relpath)) || relpath` (это же снимает открытый вопрос §11.1 — ответ «включать»); в запись файла добавить `u32be(mode)`; сортировку задать по байтам UTF-8, а нормализацию NFC убрать или явно отвергать имена, у которых NFC≠NFD-форма (иначе digest не различает две разные раскладки).
**Как проверить:** мутант «удалить пустой каталог из staging → digest расходится, шаг 6 даёт 10»; юнит-тест на путь с `é` в NFD и NFC — digest разный (или отказ); мутант `chmod 0644→0777` → digest расходится.

### 4. §7.4 → rootless невыполним для типового случая, root-assisted оставляет root-owned файлы и противоречит §2.3
Типовой legacy-инстанс (`§3`: «установка требует root») — это `/var/nemeq` с владельцем `root` или сервисным uid из `User=nemeq`. Сервисный uid — это «файл третьего uid», по `§7.4` отказ **в обоих режимах**; root-owned — rootless неприменим. То есть штатный путь миграции любого нормально установленного инстанса — root-assisted, и «работа без root» из `§8.8` к миграции не относится. При root-assisted: `chown -R` не входит в allow-list `§2.3` (там только `systemctl`) — прямое противоречие; `chown` не сбрасывает режимы, копирование под root с чужим umask расширит права против `§4.7`; `run/migration.json` и `run/migration-report.json` пишет root и **не** chown'ит → сервис пользователя не может их перезаписать, а `§8.8.8` («UID всех файлов в HOME равен владельцу») падает своей же приёмкой; проверки, что `--target-uid` совпадает с владельцем `<home>/config/home.toml`, нет — root может отдать стор чужому uid. Кода отказа для «файлы чужого uid» в `§7.9` нет, хотя таблица заявлена полной.
**Предложение:** добавить третий режим или явное правило `--adopt-uid N` (перенос владельца из источника в целевой uid с записью в отчёт), чтобы сервисный-uid-стор мигрировался без ручного `chown`; `chown` реализовать через `os.chown`/`os.lchown` (не exec) и внести в §2.3; после копирования прогонять нормализацию режимов (`0600`/`0700` по `§4.7`) и chown **всего**, включая `run/`; добавить проверку `--target-uid == st_uid(home.toml)`; добавить в `§7.9` код для отказа по чужому uid.
**Как проверить:** фикстура «стор принадлежит сервисному uid» → миграция проходит без ручных действий; после root-assisted `find HOME ! -uid N` пусто; `stat` на `run/migration.json` = 0600 и uid N.

### 5. §7.10 → `instance_id` при двух копиях одного стора: обе ветки ломают инвариант §6.1
Если `instance_id` генерируется при каждой установке — две копии одного стора получают разные id, и утверждение `§6.1` «`instance_id` идентифицирует **стор**» неверно; расхождение копий становится необнаружимым, а `§7.10` как раз хочет его ловить. Если id копируется вместе с данными — шаг 5 даёт коллизию и код 5, то есть «переход двух уже развёрнутых HOME» (заголовок сценария) не проходит для второго HOME. Кроме того, копирование `var/` копирует метаданные стора с тем же `instance_id`, поэтому сверка `§6.1` «конфиг против метаданных стора» после миграции тождественно проходит и коллизию обнаружить не может — только по списку инстансов. И противоречие внутри шага 4: «`lib/` берётся из `--use-lib-from`, а не из источника», а в примере команды `--use-lib-from /root/.nemeq`, то есть из источника; шаг 2 при этом сравнивает схему с «поддерживаемой целевым `lib/`», который ещё не выбран.
**Предложение:** развести две сущности: `store_id` (в метаданных стора, переезжает с данными, неизменяем) и `instance_id` (новый при каждом `migrate --into-instance`), плюс `lineage: {origin_home_id, origin_instance_id, migrated_at}` в `instance.toml`. Коллизию ловить по `store_id`, а не по `instance_id`; при совпадении `store_id` с уже существующим инстансом — код 5 с указанием обоих путей и сравнением digest (копии/дивергенция). `--use-lib-from` сделать обязательным и не равным источнику, либо убрать и брать lib целевого HOME.
**Как проверить:** две фикстуры-копии одного стора → вторая миграция даёт код 5 и называет первый инстанс; две фикстуры с разными `store_id` → обе мигрируют, `grep -c instance_id` уникален по инстансам.

### 6. §6.5 → защита `lib/` обещана сильнее, чем даёт user-unit; `ReadWritePaths` фиксирован, а §5 разрешает переопределять стор
`ProtectSystem=strict`/`ReadOnlyPaths` в **user**-юните применяются только при доступных unprivileged user namespaces; если их нет, systemd не отказывается, а применяет unit **без** песочницы (в лог — предупреждение). Значит «Попытка записи в `lib/` из-под unit → отказ» — не гарантия, а зависящее от хоста поведение; тест на конкретной машине зелёный, на целевой — красный. Второе: юнит генерируется `install-unit` с абсолютными `NEMEQ_HOME`/`ReadWritePaths`, а `§5` разрешает `--store`/`NEMEQ_STORE`/`--state-root` вне `<home>` (с флагом) — тогда сервис либо не может писать в стор, либо оператор руками расширяет `ReadWritePaths`, и сужение из B9 испаряется. Третье: `ReadOnlyPaths=lib` не мешает записи в `bin/`, `config/home.toml` и в `var/` **других** инстансов, если они попадут в `ReadWritePaths` при `--state-root`.
**Предложение:** понизить формулировку до best-effort и добавить runtime-самопроверку: `serve` на старте читает `/proc/self/mountinfo`/`/proc/self/status` и пишет в `run/instance.json` фактические флаги (`NoNewPrivs`, ro-монтирование `lib`); `doctor` требует их наличия для «hardened»-профиля. `install-unit` должен брать пути из `nqctl env --json`, а при расхождении фактического `store_realpath` с юнитом — отказ при старте с явным текстом «regenerate unit».
**Как проверить:** тест на хосте с `kernel.unprivileged_userns_clone=0` → сервис либо отказывается стартовать в профиле hardened, либо помечает себя не-hardened (и приёмочный критерий это видит); тест «`NEMEQ_STORE` вне HOME» → понятная ошибка, не EACCES в логах.

### 7. §8.1 → паттерн не покрывает `/var/lib/nemeq` (названный в §3!) и не покрывает целые классы файлов
Регексп `/(var|opt|run)/nemeq` не матчит `/var/lib/nemeq`, хотя `§3` перечисляет его как один из четырёх legacy-каталогов; правила для него нет и в `§4.1` (там только элементы **внутри** `/var/nemeq/`), то есть существующая установка с `/var/lib/nemeq` не мигрируется и не отвергается — просто игнорируется, данные остаются. `§10` D7 помнит про `~/.nq`, но не про `/var/lib/nemeq`. По охвату: pathspec не включает файлы без расширения (`bin/*` шимы — до их удаления по `§9`), `*.json` (`nq.json`, `INSTALL.json`, `instance.json`, `*.dist-info/RECORD`), шаблоны, из которых рендерятся юниты (`*.j2`/`*.tmpl`, а `install_unit.py` их почти наверняка использует), `*.yml`/`*.yaml` (CI, compose), `Makefile`/`Dockerfile`, `*.socket`/`*.timer`/`*.conf` (drop-in'ы), `*.pth` в колёсах; `git grep` не смотрит нетронутые индексированные файлы и бинарники, то есть сгенерированный `lib/` не проверяется вообще.
**Предложение:** инвертировать тест — сканировать **все** файлы репозитория (`rg -a --hidden -g '!.git'`) с allow-list исключений (`massaru/legacy.py`, `docs/**`, `tests/fixtures/**`), а не deny-list расширений; расширить паттерн до `/(var|var/lib|opt|usr/local|etc|run)/nemeq` и `\.nq\b`; отдельным тестом проверять, что каждый legacy-путь из `§3` имеет строку в `§4.1`.
**Как проверить:** мутанты в `.j2`, `.json`, `bin/`-скрипте без расширения и `/var/lib/nemeq` в `.py` → тест падает в каждом; тест «каждый путь из §3 присутствует в таблице §4.1» — мутант: удалить строку → падает.

### 8. §0 против §8.3, §8.7, §8.8 → правило «у каждого критерия есть мутант» нарушено собственной спецификацией
`§8.3`: заявленный критерий — инварианты `rev`/`last_hash`/`identity` через restart, а мутант — «остановить стор → health non-200». Это проверка доступности, не инварианта: сломайте сверку `instance_id` или сбросьте `rev` при рестарте — тест останется зелёным, потому что остановленный стор всё равно даёт non-200. `§8.7` (10 негативных сценариев) и `§8.8` (8 пунктов) вообще не имеют мутантов, хотя по `§0` критерий без мутанта недействителен — то есть два раздела целиком не проходят правило, которое они же декларируют.
**Предложение:** для `§8.3` заменить мутант на «в `instance.toml` подменить `instance_id` при живом сторе → health отдаёт non-200 с кодом 5» и «подменить `rev` на меньший в ответе → тест падает»; для `§8.7`/`§8.8` дописать по мутанту на пункт (например, `§8.8.2`: сделать `install` неидемпотентным — перегенерировать `home_id` → тест падает; `§8.8.8`: `chown` одного файла → тест падает).
**Как проверить:** формальный линтер по `docs/architecture/*.md`: у каждого критерия `§8.x` есть строка «Мутант:» и она непустая; отдельный тест-«метамутант» — прогнать каждый мутант и убедиться, что соответствующий тест действительно краснеет (иначе мутант вакуумный).

## Вердикт

**Не готово к реализации.**

Блокеры:
1. `§6.4`+`§7.3`+`§7.2`+`§6.3` — lock внутри стора: невоспроизводимый `store_digest`, копирование lock при миграции, потеря лока после `rename`, race при `destroy`.
2. `§7.2` — нет состояния для окна `rename`→`published`; повторный запуск из `verifying` не продолжается и не откатывается; манифест миграции остаётся внутри опубликованного `var/`.
3. `§7.3` — длина в `len()` не задана в байтах (риск коллизий); пустые каталоги вне digest, критерий `§8.4` вакуумный относительно них; режимы прав не покрыты.
4. `§7.4` — rootless неприменим к типовому (root/сервисный uid) стору, root-assisted оставляет root-owned `run/*`, использует запрещённый `§2.3` `chown`, не проверяет `--target-uid` против владельца HOME.
5. `§7.10` — `instance_id` не может одновременно идентифицировать стор и быть уникальным для инстанса; копии одного стора либо не ловятся, либо не мигрируют; `--use-lib-from` противоречит своему же шагу 4.

Серьёзные, но не блокирующие (закрываются формулировкой, не переработкой): `§6.5` (обещание песочницы сильнее фактического поведения, статический `ReadWritePaths` против переопределений `§5`), `§8.1` (пропущен `/var/lib/nemeq` и целые классы файлов), `§0` против `§8.3`/`§8.7`/`§8.8` (вакуумный мутант и два раздела без мутантов).
