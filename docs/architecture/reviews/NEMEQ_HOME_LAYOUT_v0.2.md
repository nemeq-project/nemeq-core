## 0. Принципы

### 0.1 Что означает «self-contained» — два разных утверждения

**(а) Нет сетевых и пакетных зависимостей.** Проверяемо и обязательно:

- нет `pip install` из сети, нет `ensurepip`, нет `virtualenv` на машине установки;
- нет обращений к `pypi.org`, зеркалам и любым реестрам во время install и запуска;
- установка на машине без сети — штатный режим;
- отсутствие `pip`/`ensurepip` в `PATH` является **нормальным**, а не поводом падать.

**(б) Хостовые предпосылки объявлены и проверяются.** Ложь «зависимостей нет» выключает проверку, поэтому предпосылки названы явно и проверяются preflight:

| Предпосылка | Значение | Проверка |
|---|---|---|
| интерпретатор | CPython `>=3.12,<3.13` | `nqctl install` отказывает с кодом 2 до создания каталогов |
| архитектура | `x86_64` | `platform.machine()` |
| libc | glibc ≥ версии, под которую собраны колёса | `platform.libc_ver()`, сверка с `deps.lock` |
| ФС стора | локальная, POSIX `flock`, атомарный `rename`, `fsync` | `doctor`: `stat -f`; NFS/overlay/CIFS → отказ, код 8 |
| внешние утилиты | allow-list (§0.5) | `doctor` |

**Целевой triple для Rust-этапа:** `x86_64-unknown-linux-musl`. Иначе «статический бинарь» унаследует ту же glibc-зависимость, что и колёса, и Rust-переписывание не закроет (б).

### 0.2 Целевая платформа — Rust

Переходное правило: Python-поставка обязана вести себя так, будто Rust-бинарь уже есть — переносимо, без зависимости от окружения хоста. Всё, что нарушает, — техдолг D1–D7 (§9) с датами.

### 0.3 Барьер `sys.path`

При старте любой точки входа `sys.path` очищается до:

1. `$NEMEQ_HOME/lib/nemeq-core`
2. `$NEMEQ_HOME/lib/pydeps` (через `site.addsitedir`, не `PYTHONPATH`)

Всё остальное удаляется. Если импорт пришёл не из `lib/` — приложение падает с явной ошибкой, а не деградирует молча.

**Критерий:** в рантайме `sys.path` не содержит `/usr/lib/python3/dist-packages`, `/usr/lib/python3/site-packages`, `~/.local/lib/...`.

### 0.4 Поставка зависимостей

Wheel-архив — источник истины, распаковка при install:

1. `wheelhouse/` + `wheelhouse/manifest.sha256` приезжают с дистрибутивом;
2. `nqctl deps install --from wheelhouse/` — обычный zip-распаковщик, без `pip`;
3. sha256 каждого колеса сверяется с манифестом до распаковки;
4. сохраняется `.dist-info` (иначе ломается `importlib.metadata`);
5. `RECORD` внутри колеса проверяется пофайлово;
6. предкомпилированные `.pyc` приезжают в поставке.

**Критерий:** `nqctl deps verify` возвращает 0 на исправной установке и ≠0 после подмены одного байта в любом файле `lib/pydeps` или в колесе.

### 0.5 Allow-list внешних утилит

Разрешено вызывать только: `systemctl` (опционально, с fallback), `systemctl --user`. Всё остальное — внутрипроцессно (`shutil.copy2` + явные режимы + `os.fsync`). `cp`, `rsync`, `sha256sum`, `unzip` — **не вызывать**.

**Критерий:** `strace -f -e trace=execve` на `install` и `migrate` не показывает `execve` вне allow-list.

## 1. Проблема

Пути ОС общие на всю машину, из-за чего:

1. два инстанса конфликтуют (общий `flock`, общий стор);
2. установка требует root;
3. удаление — ручная зачистка четырёх разнесённых каталогов;
4. инстанс нельзя перенести на другую машину.

Проверено на `c-nemeq`: `/opt/nemeq`, `/var/nemeq`, `/var/lib/nemeq`, `/run/nemeq` были пусты — ни одной установки.

## 2. Аналоги

**Hermes — `~/.hermes`.** Корень состояния в домашнем каталоге, инстанс различается переменной `HERMES_HOME` на процесс; в bridge `HERMES_HOME_ROOT=/var/lib/hermes-runtime-bridge/homes/<session_id>`.

**OpenCode — XDG.** `~/.config/opencode` (конфиг), `~/.local/share/opencode` (данные), переопределение `OPENCODE_CONFIG_DIR`/`OPENCODE_DB`. Второй инстанс — обёртка над тем же бинарём с другим окружением.

Оба держат состояние в home и различают инстанс переменной либо каталогом. Ни один не пишет в `/opt` и `/var` ОС.

## 3. Раскладка

```
$NEMEQ_HOME/                      # префикс; по умолчанию ~/.nemeq
├── bin/                          # шимы: nqctl, nemeq-apiserver, nemeq-massaru
├── config/                       # instance.toml, nq.json
├── lib/                          # immutable: код и зависимости
│   ├── nemeq-core/
│   ├── pydeps/
│   └── INSTALL.json              # манифест установки (§3.5)
├── instances/<name>/             # инстанс (по умолчанию "default" — плоско)
│   ├── config/
│   ├── var/                      # mutable-корень
│   │   ├── store/
│   │   ├── epishu/<id>/
│   │   ├── state/
│   │   ├── data/
│   │   ├── tmp/
│   │   └── pycache/
│   ├── logs/
│   └── run/
└── var -> instances/default/var  # симлинк для плоского дефолта
```

### 3.1 Отображение старых путей — строго 1:1

| Было | Стало |
|---|---|
| `/var/nemeq` | `$NEMEQ_HOME/instances/<name>/var` |
| `/var/nemeq/apiserver` | `.../var/store` |
| `/var/nemeq/epishu` | `.../var/epishu` |
| `/var/nemeq/state` | `.../var/state` (без вложения `state/state`) |
| `/var/nemeq/data` | `.../var/data` |
| `/opt/nemeq` | `$NEMEQ_HOME/lib` |
| `/run/nemeq` | `$NEMEQ_HOME/instances/<name>/run` |

**Критерий:** функция `map_legacy(p)` даёт путь, который после `migrate` существует тогда и только тогда, когда существовал `p`; тест на фикстуре всех семи элементов.

### 3.2 Контракт `epishu/<id>/` не меняется

Дерево `wal/ atoms/ traces/ state/ view/ paqidutu/ zikru-zi/ zikru-su/ raw/ archive/ observability_log/` сохраняется полностью. Меняется только корень.

**Три вещи, которые ломают контракт, и их запрет:**

1. **Абсолютные пути внутри данных.** В атомах, трейсах, `observability_log` хранятся только пути относительно `<store_root>`. `fsck` находит и репортит любую строку, начинающуюся с `/` в метаданных.
2. **ФС стора.** `$HOME` может быть NFS/overlay, где `flock`/`rename` не дают гарантий TEXTSTORE. `doctor` проверяет `stat -f`, NFS/overlay/CIFS → отказ с кодом 8.
3. **Глубина вложенности.** Код не должен вычислять пути от количества уровней — только через `resolve_home()`.

### 3.3 `lib/` действительно immutable

Первый запуск создаёт `__pycache__` рядом с исходниками, что ломает декларацию и шаринг между инстансами. Поэтому:

- `PYTHONPYCACHEPREFIX=$NEMEQ_HOME/instances/<name>/var/pycache` в шимах;
- `PYTHONDONTWRITEBYTECODE=1` для дочерних процессов;
- `chmod -R a-w lib/` при install;
- предкомпилированные `.pyc` в поставке (§0.4).

**Критерий:** после полного прогона (install → start → тесты → stop) `find lib -newer lib/INSTALL.json` пуст; старт при `chmod -R a-w lib` проходит без ошибок.

### 3.4 `var/tmp/` обязателен

`rename` атомарен только в пределах одной ФС. Staging в `/tmp` (tmpfs) даст `EXDEV` или неатомарную подмену.

- `var/tmp/` (0700) — все атомарные записи и staging;
- `os.replace` только внутри `var/`;
- `doctor` сверяет `st_dev(var/tmp) == st_dev(var/epishu)`.

**Критерий:** `rename` из `var/tmp` в `var/epishu/<id>/wal` не даёт `EXDEV`; `doctor` падает при разных ФС.

### 3.5 Манифест установки

`$NEMEQ_HOME/lib/INSTALL.json`:

```json
{
  "layout_version": 2,
  "nemeq_version": "0.1.0",
  "schema_version": 4,
  "platform_tag": "cp312-manylinux_2_17_x86_64",
  "deps_lock_sha256": "...",
  "build_id": "...",
  "installed_at": "..."
}
```

`config/instance.toml` содержит `schema_version` инстанса. Код отказывается открывать стор со схемой новее своей.

**Критерий:** `nqctl doctor --json` печатает оба манифеста и результат сверки; при `schema_version` в `instance.toml` на +1 сервис не стартует и пишет «store schema 5 > supported 4».

### 3.6 Сокеты и длина пути

`sun_path` на Linux — 108 байт. Длинный `HOME` даёт `AF_UNIX path too long` на старте демона.

- валидация всех сокет-путей в `install`/`doctor`, порог 100;
- для длинных HOME — короткий каталог `var/run-short` (0700) или abstract sockets.

**Критерий:** `HOME=/home/<40 символов>` проходит install и старт; при длине > 108 `doctor` падает заранее.

### 3.7 Квоты и права

Стор в `$HOME`: «убежавший» WAL заполнит домашний раздел.

- `install` ставит `0700` на `var/`, `0600` на файлы, `config/instance.toml` `0600` (там могут быть токены), umask `077`;
- `config/instance.toml` содержит `max_state_bytes`; soft-лимит 80 % пишет в лог;
- `doctor` проверяет права и свободное место;
- документация: бэкап `$HOME` исключает `var/store`.

**Критерий:** `install` при umask 000 даёт `stat -c %a var` = 700; `doctor` ≠0 при `var` = 755 или при свободном месте < `max_state_bytes × 2`.

### 3.8 `run/` без overlay

Overlay — это `mount()`, то есть root, что возвращает проблему §1.2.

- `run/` — только pid, lock, сокеты, `instance.json`;
- overlay либо `var/overlay/` (copy-on-write каталог), либо уровень (в) и вне этого документа.

**Критерий:** в §3 у `run/` нет слова overlay; установка и запуск проходят под непривилегированным UID без `CAP_SYS_ADMIN`.

## 4. Резолвинг — три независимые цепочки

Одной цепочки недостаточно: `--home`, `--state-root` и `--store` — разные корни.

```
home:  --home       > NEMEQ_HOME     > $HOME/.nemeq
var:   --state-root > NEMEQ_VAR_ROOT > <home>/instances/<instance>/var
store: --store      > NEMEQ_STORE    > <var>/store
instance: --instance > NEMEQ_INSTANCE > "default"
```

**Правила:**

1. Все переопределения обязаны быть абсолютными. Относительный путь — ошибка с кодом 2, **не** «приведём от CWD».
2. `--state-root` / `--store` вне `<home>` допустимы только с `--allow-outside-home`.
3. При использовании env-переопределений — строка `source=env(NEMEQ_VAR_ROOT)` в `nqctl status`.
4. `$HOME` отсутствует или пуст, и нет `--home`/`NEMEQ_HOME` → **отказ с кодом 2**. Никогда не фоллбэчить на CWD или `/`.
5. Каталоги создаёт только `nqctl install` / `migrate`. `apiserver` без `init` падает с `NemeqNotInitialized`, а не создаёт мусор.

**Критерий:** параметризованный тест «8 комбинаций флагов/env → 3 ожидаемых пути + источник»; `env -u HOME bin/nqctl status` → код 2; `env HOME= ...` → код 2; относительный `NEMEQ_HOME=./x` → код 2.

## 5. Инстансы

### 5.1 Два разных понятия

- **`NEMEQ_HOME`** — префикс: `bin/`, `lib/`, `config/`.
- **`NEMEQ_INSTANCE`** — имя под `$NEMEQ_HOME/instances/<name>/`: `config/`, `var/`, `logs/`, `run/`.

Только так `lib/` действительно общий, а данные изолированы. Вариант «профиль = отдельный HOME» (v0.1 §5а) был физически невозможен: `--home` — это корень с `lib/`, значит профиль тащил свою копию кода.

**Правило выбора механически:** разные UID или разные версии — разные `NEMEQ_HOME`; иначе — инстансы в одном HOME.

**Критерий:** `nqctl --home A --instance alpha` и `... --instance beta` — в `A/lib` один экземпляр кода (`find A/lib -maxdepth 1 | wc -l` не растёт); `nqctl instance list` показывает оба.

### 5.2 Идентичность и порты

- `home_id` (UUID) генерируется при install в `config/instance.toml` **и** в метаданных стора; при старте сверка, расхождение → отказ с кодом 5.
- Порт по умолчанию `0` (эфемерный) либо явный в `instance.toml`; фактический порт пишется в `run/instance.json` (`{name, home_id, pid, port, started_at}`).
- `EADDRINUSE` → код 3 с именем инстанса-виновника (поиск по `instances/*/run/instance.json`).

**Критерий:** два инстанса с одинаковым портом — второй завершается non-zero, ничего не пишет в стор, сообщение называет виновника.

### 5.3 Лок

Корень исходной проблемы — общий `flock`. Лок строго:

```
$NEMEQ_HOME/instances/<name>/run/store.lock
open(O_RDWR|O_CREAT|O_NOFOLLOW, 0600)
flock(LOCK_EX|LOCK_NB)
```

Занят → код 4 и «store busy: pid N». Любые фиксированные пути вне HOME запрещены.

**Критерий:** второй процесс на том же инстансе падает за <1 с с кодом 4; на разных — оба живы; `strace` показывает один `openat` lock-файла внутри HOME.

### 5.4 systemd — user-unit, `%h` запрещён

Системный `/etc/systemd/system` требует root и нарушает §0.1.

- дефолт: `~/.config/systemd/user/nemeq-<instance>.service`, `systemctl --user enable --now`;
- системные unit — только уровень (в);
- абсолютный `NEMEQ_HOME` прописывает генератор `nqctl install-unit`; **`%h` не использовать** — в системном юните он даёт HOME менеджера (root), а не `User=`;
- в шаблоне: `Environment=NEMEQ_HOME=<abs>`, `Environment=NEMEQ_INSTANCE=<name>`, `ExecStart=<abs>/bin/nqctl serve`, `Restart=on-failure`, `KillMode=mixed`, `TimeoutStopSec=20`;
- доступная часть уровня (в) уже сейчас: `NoNewPrivileges=yes`, `PrivateTmp=yes`, `ProtectSystem=strict`, `ReadWritePaths=<abs>`, `ProtectHome=read-only` с исключением для HOME инстанса.

**Критерий:** установка и `systemctl --user start` без sudo; `systemd-analyze verify` на сгенерированном unit; `grep -c '%h' unit` = 0.

### 5.5 Жизненный цикл

`nqctl instance create|list|status|destroy`:

- `create`: `0700` на каталоги, `0600` на конфиг, `run/` `0700`;
- `destroy`: требует остановленного сервиса, берёт лок, удаляет только `var/ config/ logs/ run/`, `lib/` не трогает;
- `list`/`status` — машинно-читаемый JSON.

**Критерий:** `stat -c %a` на var/config/run = 700/600/700; `destroy` при живом сервисе отказывает с кодом 4; после destroy `lib/` на месте.

## 6. Миграция

### 6.1 Безопасность источника

- требуется **остановленный** сервис; при живом — отказ с кодом 2 и текстом «stop nemeq-<i> first»;
- `--force` не вводится;
- перед копированием проверяется и target: непустой `var/` → отказ, если не указан `--merge`.

**Критерий:** негативный тест — при запущенном сервисе `migrate` даёт код 2 и не создаёт файлов в target.

### 6.2 Атомарность

- копирование в `var.migrating-<ts>/`;
- `fsck` гоняется по staged-каталогу;
- затем `rename()` в `var/`;
- при ошибке staged удаляется;
- маркер `MIGRATION_INCOMPLETE` в `run/` до успешного rename.

**Критерий:** `kill -9` на 50 % копирования → target не содержит `var/`, есть только `var.migrating-*` и маркер; повторный запуск начинается с нуля.

### 6.3 Полнота — `store_digest`, а не `rev`+`last_hash`

`rev`+`last_hash` — это голова, а не стор: не покрывает число атомов, WAL-сегменты, `paqidutu`/`view`, anchor.

```
store_digest = sha256(
  sorted(epishu_id, rev, last_hash, atom_count, wal_segments_crc)
  + anchor_hash
)
```

Сверяется digest, а не пара. Отчёт пишется в `run/migration-report.json`.

**Критерий:** отчёт содержит digest источника и цели, они равны; подмена одного байта в `atoms` целевого стора → digest расходится, миграция не успешна.

### 6.4 Права и владелец

Миграция `/var/nemeq` (root) → `~/.nemeq` (пользователь) меняет владельца. «Сохранение прав» даст недоступный стор.

- после копирования `chown -R <target uid>:<gid>`;
- снятие setuid/setgid;
- **отказ**, если в источнике есть файлы третьих uid (не «молчаливое исправление»).

**Критерий:** `find target/var ! -user $(id -u)` пусто; `find target/var -perm /6000` пусто; фикстура с файлом root:wheel в источнике → отказ с перечислением.

### 6.5 Symlink

Абсолютные ссылки внутрь `/var/nemeq` после переезда станут висячими; разыменование вытащит данные за пределы HOME.

- копировать ссылки как ссылки, без dereference;
- абсолютные ссылки, чей target вне источника, — в отчёт и отказ по умолчанию;
- `--rewrite-links` для переписывания префикса;
- симлинк наружу источника — всегда отказ.

**Критерий:** фикстура `var/x -> /var/nemeq/var/y` → отказ, путь в отчёте; относительная ссылка внутри стора копируется как `lrwxrwxrwx`, `readlink` идентичен.

### 6.6 Anchor и незавершённые транзакции

Явный перечень копируемого: `store/`, `var/epishu/`, `var/state/`, `var/data/`, **`anchor*`**, `wal/`, `paqidutu/`, `view/`, `zikru-*`, `observability_log/`.

fsck источника — strict. При непустом хвосте WAL:

- по умолчанию отказ с кодом 6;
- `--recover` реплеит WAL в staged-копию, после чего `rev` сравнивается **после** реплея на обеих сторонах.

**Критерий:** фикстура с оборванной транзакцией → код 6 и перечень записей; с `--recover` — rev совпадает, отчёт фиксирует число реплеенных записей и что источник не изменялся (mtime/размер до и после).

### 6.7 Источник по умолчанию НЕ удаляется

- дефолт — не удалять;
- `--purge-source` только после: успешного fsck + старта сервиса на target + health ok + write/read roundtrip;
- в отчёт пишется готовая команда удаления, чтобы оператор выполнил её сам.

**Критерий:** после `migrate` без флага источник на месте; с `--purge-source` при падении сервиса на target — источник на месте, код non-zero.

### 6.8 Карта путей, неизвестные записи, version skew

- `--dry-run` печатает полное отображение и **падает** (код 7) на любой записи без правила;
- в отчёт пишутся `source_version`, `target_version`, `format_version`; отказ, если версия вне поддерживаемого диапазона;
- отдельный шаг: `systemctl --user disable --now nemeq-<old>` + печать новых unit-команд (старый unit после миграции иначе поднимет инстанс на удалённых путях).

**Критерий:** `--dry-run` на фикстуре с «лишним» файлом → код 7 и имя файла; на чистой фикстуре — полная таблица, ни одного шага «прочее/остальное».

### 6.9 Коды возврата `migrate`

| Код | Значение |
|---|---|
| 0 | успех |
| 2 | источник занят / target непуст / неверный аргумент |
| 4 | лок не взят |
| 5 | `home_id` не совпадает |
| 6 | грязный WAL, нужен `--recover` |
| 7 | неизвестная запись, нет правила |
| 8 | неподдерживаемая ФС |
| 9 | расхождение хеша поставки |

## 8. Критерии приёмки

### 8.1 Ни одного пути ОС в коде

```sh
git grep -nE '/(var|opt|run)/nemeq' -- '*.py' ':!massaru/legacy.py' ':!tests/fixtures/*'
```
должно быть пусто.

Плюс архитектурный тест: строки допустимы **только** в `massaru/legacy.py`.

**Самопроверка критерия:** тест обязан падать, если добавить `/var/nemeq` в любой другой файл, и оставаться зелёным, если добавить его в `legacy.py`. Без этой проверки критерий считается недействительным.

### 8.2 Изоляция инстансов доказана данными

Автотест, а не ручная проверка:

- один и тот же id записан в alpha и beta с **разным** содержимым;
- оба читаются независимо и корректно;
- `realpath` двух сторов не пересекаются, inode разные;
- второй старт на том же инстансе → код 4.

**Самопроверка:** при подмене `NEMEQ_HOME` beta на alpha тест обязан падать (иначе он тавтологичен).

### 8.3 Health как контракт

Эндпоинт обязан отдавать `{instance, home_id, rev, last_hash, fsck: clean}`.

До и после `systemctl --user restart`: `rev` не убывает, `last_hash` совпадает, `instance`/`home_id` те же. Проверка от имени владельца HOME.

**Самопроверка:** при остановленном сторе health отдаёт non-200.

### 8.4 Миграция — через `store_digest`

Сравнивается digest (§6.3), не пара `rev`+`last_hash`.

### 8.5 Чистота вне HOME

Метод: `strace -f -e trace=openat,mkdir,mkdirat` на `install` + первый запуск; фильтр по `O_CREAT|O_WRONLY` вне HOME.

Allow-list исключений перечислен явно: `/dev/null`, `/proc/self`, сокет systemd, `$XDG_RUNTIME_DIR` (если разрешён — то осознанно).

Отдельным пунктом: `PYTHONDONTWRITEBYTECODE=1` + `.pyc` в поставке, `lib/` ro.

### 8.6 Установка без сети и без pip

Два прогона:

1. `unshare -n` — установка и старт проходят;
2. с сетью + `strace -e connect,sendto` — **ноль** попыток наружу.

Плюс: `pip`/`ensurepip` отсутствуют в `PATH` тестового окружения (проверяется в самом тесте); smoke-импорт каждого пакета из `deps.lock`.

### 8.7 Негативные сценарии миграции

Каждый — отдельный тест с ожидаемым кодом и состоянием target:

| Сценарий | Код |
|---|---|
| сервис запущен | 2 |
| target непуст | 2 |
| неизвестная запись при `--dry-run` | 7 |
| грязный WAL | 6 |
| симлинк наружу | 7 |
| `kill -9` посреди копирования | staged удалён, маркер есть |
| файл третьего uid | отказ с перечнем |

### 8.8 Чего не было в v0.1

1. установка и работа от непривилегированного пользователя, без sudo;
2. идемпотентность: повторный `install` поверх существующего HOME сохраняет `rev`/`last_hash` и не плодит инстансы;
3. `nqctl uninstall [--purge]` не оставляет процессов, лок-файлов, unit'ов;
4. гонка старта: два одновременных запуска на одном инстансе — ровно один жив;
5. HOME с пробелом и не-ASCII в пути;
6. поведение на NFS: отказ при старте с кодом 8;
7. `nqctl doctor --json` как машинно-читаемый артефакт приёмки;
8. проверка прав: UID всех файлов в HOME равен владельцу.

## 10. Открытые вопросы (для ревью v0.2)

1. **`instances/default` + симлинк `var -> instances/default/var`.** Симлинк удобен для совместимости с уже развёрнутыми alpha/beta, но добавляет вторую точку, где путь может «уехать». Оставить симлинк или требовать явный `--instance default` везде?
2. **Порт по умолчанию `0` (эфемерный).** Удобно для параллельных инстансов, но неудобно клиентам: адрес меняется при каждом старте. Эфемерный или фиксированный `8448` с автоинкрементом?
3. **`store_digest` по всем `epishu_id`.** На большом сторе (1M rev) полный обход может быть медленным. Считать по всем или по выборке с отдельной проверкой полноты через `fsck`?
4. **`--purge-source` требует write/read roundtrip на target.** Это меняет `rev` на target. Допустимо ли, или roundtrip делать на отдельном временном ключе, который потом удаляется?
5. **T-01a (`lib/` ro + EACCES без root).** Достаточно ли `chmod 0555` + попытка записи от владельца, или нужен реальный ro-mount (что опять требует root)?
