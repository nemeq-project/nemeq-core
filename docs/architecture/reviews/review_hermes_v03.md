4. Блокер — §§6.4, 7.2, lock внутри стора конфликтует с копированием и удалением

Замечание — миграция удерживает lock в `<store>/lock`, но одновременно переносит данные стора. Копирование lock-файла не переносит `flock`; если целевой lock уже открыт процессом, замена или перезапись файла может оставить lock на старом inode, а новые процессы смогут заблокировать новый inode. К тому же §7.3 включает этот изменяемый lock в digest. При `destroy` удаляется каталог с lock-файлом, пока команда держит lock: другой процесс может создать новый lock-файл и получить блокировку на другом inode. Для read-only store обязательный `O_RDWR|O_CREAT` тоже завершится ошибкой, но режим read-only не определён.

Предложение — исключить lock из копируемого содержимого и digest, создавать и удерживать целевой lock на конечном inode отдельно от миграционного payload. Для `destroy` определить стабильную блокировку жизненного цикла, которая не исчезает вместе с `var/`, либо другой атомарный механизм, исключающий параллельный старт. Явно запретить read-only stores с ранней диагностикой либо определить для них отдельный режим блокировки.

Критерий проверки — конкурентный старт во время `destroy` и миграции никогда не получает доступ через новый inode; lock не входит в payload/digest; read-only store либо предсказуемо отвергается до изменений, либо проходит документированный тест.
